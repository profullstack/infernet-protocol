## Abstract

Anyone can post a training job with a budget; any opted-in operator on
the network can race-claim shards, run them, and report back for
payment. Training shards are a first-class auction surface — same shape
as inference jobs, paid through the same CoinPay receipts (IPIP-0007).
A submitter never has to know which nodes will pick up the work, and
no single greedy node can monopolize a job because the daemon enforces
one in-flight shard per operator.

## Motivation

Federated training under IPIP-0011 / IPIP-0023 assumed the submitter
already had a private fleet of trusted operators. Anyone wanting to
train a custom model with the help of strangers had to build their own
discovery, queueing, and payout pipeline on top.

We want a "post a job, walk away" experience: the submitter splits a
local JSONL into N shards, posts the job with a budget, and the global
network of opted-in nodes drains the queue. The submitter is billed
per shard; operators are paid per shard. No coordinator, no preassigned
fleet.

## Specification

### Schema

Two new tables (Supabase migration):

- `training_jobs`
  - `id uuid pk`
  - `submitter_pubkey text` — Nostr pubkey of the user posting the job
  - `model text` — base model id (e.g. `qwen2.5:0.5b`)
  - `config jsonb` — training hyperparameters (LoRA rank, lr, epochs, …)
  - `shard_base_url text` — `s3://`, `https://`, or daemon-hosted URL
    where shards are fetched from
  - `total_shards int`
  - `budget_total numeric` — operator-payable pool in USD
  - `min_vram_gb int` — gating filter for which operators can claim
  - `status text` — `posted | running | completed | cancelled`
  - `created_at timestamptz`

- `training_shards`
  - `id uuid pk`
  - `job_id uuid fk → training_jobs(id)`
  - `index int` — 0-based shard ordinal
  - `shard_url text` — full URL to fetch this shard's JSONL
  - `status text` — `pending | claimed | running | completed | failed`
  - `claimed_by_pubkey text` — operator who won the race
  - `claimed_at timestamptz`
  - `result_url text` — URL of the LoRA weights / checkpoint produced
  - `report_payload jsonb` — operator-supplied metrics

### API surface

All endpoints sit under `/api/v1/training/`. Operator-side endpoints
require IPIP-0003 signed-request auth; submitter-side endpoints require
the user's session JWT.

- `POST /api/v1/training/jobs` (user-authed)
  - Body: `{ model, config, shard_urls: string[], budget_total, min_vram_gb }`
  - Server creates the `training_jobs` row + N `training_shards` rows
    (one per `shard_urls` entry), all in `pending`.

- `POST /api/v1/training/shards/available` (signed)
  - Body: `{ vram_gb }`
  - Returns up to 16 `pending` shards whose `min_vram_gb ≤ vram_gb`,
    excluding any job the operator's pubkey already has a claimed
    shard in (so a busy operator doesn't churn polling).

- `POST /api/v1/training/shards/<id>/claim` (signed)
  - Atomic compare-and-set: `UPDATE … SET status='claimed',
    claimed_by_pubkey=…, claimed_at=now() WHERE id=$1 AND
    status='pending'`. Returns 409 if another node already won.

- `POST /api/v1/training/shards/<id>/report` (signed)
  - Body: `{ status: "completed" | "failed", result_url?, metrics? }`
  - Server validates `claimed_by_pubkey` matches the signing pubkey,
    moves the shard to its terminal state, and emits a CPR receipt
    against the job's `budget_total` per IPIP-0007.

### Daemon behavior

- Opt-in via `INFERNET_ACCEPT_TRAINING=1` (or `engine.acceptTraining=true`
  in the operator config). Default: off.
- A new `pollTrainingMarket()` loop runs every 60s alongside the
  existing job + command polls. It calls `/shards/available`, picks one,
  attempts `/shards/<id>/claim`, and runs the same Unsloth runner used
  by `runTrainShard` (IPIP-0023) on success.
- A `trainingBusy` guard means **one shard at a time per node**. A
  greedy operator with a 10× faster GPU still only holds one shard at a
  time, so a small swarm can still finish a large job.

### Submitter CLI

```sh
infernet train run --open-market \
                   --shard-base-url s3://… \
                   --budget 5.00 \
                   --max-nodes 8 \
                   --config X.yml
```

Splits the local JSONL into `--max-nodes` shards, uploads them to
`--shard-base-url`, and posts the job with `total_shards = max-nodes`
and `budget_total = budget`. Prints the dashboard URL where the
submitter can watch shard claims and completions land.

## Rationale

Alternatives considered:

1. **Assigned-fleet model (status quo IPIP-0011)** — submitter picks
   nodes by hand. Doesn't scale, can't be advertised as a public good.
2. **Auction with bids** — operators bid on shards, lowest bidder wins.
   More market-efficient, but adds a round-trip and a price-discovery
   surface to every shard. Race-claim with a uniform per-shard price
   (`budget_total / total_shards`) ships in one PR.
3. **DHT-coordinated** — no central control plane. Deferred to a future
   IPIP; we want the simplest thing that works first.

The hard constraint behind the "one shard at a time per node" rule is
fairness: a 100-shard job posted on a Saturday should not be drained
in 30 minutes by one well-connected H100, leaving every other operator
with nothing to do. Per-operator concurrency caps make the queue feel
like a many-hands market rather than a single-winner auction.

## Backwards compatibility

- New tables only. Existing `jobs` / `nodes` / `payments` schema
  unchanged.
- Operators not running the new daemon never see training shards and
  are unaffected.
- The `infernet train run` subcommand keeps its existing federated /
  local modes; `--open-market` is additive.

## Test plan

- Unit: `tests/training-market.test.js` covers race-claim atomicity,
  per-operator concurrency, and signed-request enforcement.
- Integration: post a 4-shard job from the CLI against a 2-node
  testnet; assert both nodes drain shards alternately and the
  receipts add up to `budget_total`.

## Security considerations

- Race-claim is atomic in Postgres (`WHERE status='pending'`); two
  operators claiming the same shard cannot both succeed.
- A malicious submitter could post a job with adversarial training
  data hoping operators leak weights or compute. Mitigation: shards
  are sandboxed in the daemon's training runner, no operator state
  leaves the runner, and operators MAY refuse jobs from unknown
  submitter pubkeys (future filter).
- A malicious operator could `/report` a fake `result_url`. The
  submitter validates checkpoints client-side; a bad shard is
  re-posted by the submitter, and the operator's pubkey can be
  excluded from future jobs.

## Privacy considerations

The submitter's pubkey and shard URLs are public on the control plane,
so anyone can see which jobs are open. Operators reveal their pubkey
when they claim. No new linkable telemetry beyond what IPIP-0011
already exposed.

## Open questions

- Should `min_vram_gb` be replaced by a richer capability filter
  (model size, quantization, interconnect)? Likely yes, in a follow-up.
- Reputation: a submitter who keeps cancelling mid-job wastes operator
  time. Should we charge a non-refundable booking fee?
