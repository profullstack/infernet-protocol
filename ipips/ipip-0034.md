## Abstract

Lets browser-only clients (the chat playground, network-status
dashboards, third-party apps embedding the SDK) participate in the
Infernet Hyperswarm DHT — peer lookup, topic census, signed-handshake
verification — without having to talk through the centralized
`infernetprotocol.com` control plane. Bridges via
[`@hyperswarm/dht-relay`](https://github.com/holepunchto/dht-relay)
over WebSocket. Operators run a small `infernet relay` daemon
alongside (or distinct from) their existing inference daemon; browsers
connect to one or more relays advertised through a public list, query
the same topic keyspace defined in IPIP-0032, and corroborate results
across relays so a single malicious relay can't lie undetected.

The control plane stays out of the relay layer (per IPIP-0032 §5),
preserving the property that "the site can go dark and the network
keeps working" — a browser with at least one reachable relay still
finds peers, runs `rpc:<model>` censuses, and can populate the chat
playground's distributed-mode checkbox without the control plane
being up.

## Motivation

IPIP-0032 ships the DHT for daemons. IPIP-0033 Phase 4 adds a
control-plane census endpoint (`/api/v1/rpc/census`) so the chat
playground can decide whether to enable distributed mode — but that
endpoint reads heartbeats, not the DHT, because the control plane
MUST NOT itself join the DHT. Net effect: browsers see network state
the control plane sees. If the control plane goes down, the chat
playground is stuck even though the DHT is healthy.

For the playground to keep working when `infernetprotocol.com` is
unreachable, browsers need their own (indirect) view of the DHT.
Browsers can't run UDP, so they can't speak Hyperswarm directly.
Holepunch ships an officially supported pattern for exactly this:

- A relay daemon runs the full Hyperswarm + UDP DHT stack.
- The relay exposes a WebSocket endpoint that proxies DHT lookup
  + announce + connection traffic from JavaScript clients.
- Browser clients use `@hyperswarm/dht-relay` to dial the WebSocket,
  then call the same DHT API they would on Node — `lookup(topic)`,
  `connect(remotePublicKey)`, etc.

This IPIP defines:

1. The capability advertisement so operators can opt in to running
   a relay (`specs.dht_relay`).
2. The public list endpoint so browsers can find live relays
   without picking favorites.
3. The browser query / handshake / corroboration model.
4. The threat model — what a malicious relay can do, and what cross-
   relay corroboration buys you.

## Specification

### 1. Operator: hosting a relay

A daemon that wants to bridge browsers to the DHT MUST run the
`@hyperswarm/dht-relay` server bound to an HTTPS-fronted WebSocket
endpoint. The daemon advertises in its heartbeat:

```json
{
  "specs": {
    "dht_relay": {
      "kind": "hyperswarm-dht-relay-v0",
      "websocket_url": "wss://relay.example.com/dht",
      "version": "<package version>",
      "max_connections": <int>
    }
  }
}
```

`websocket_url` MUST be reachable over `wss://` (not `ws://`) so
browsers don't get mixed-content blocked on HTTPS pages. Operators
who can't terminate TLS themselves SHOULD front the relay with a
reverse proxy (Caddy / Cloudflare / nginx) or a tunneling service
(cloudflared / Tailscale Funnel).

Implementations MUST cap concurrent browser connections per relay
(default `max_connections: 32`) — browsers leak connections more
often than daemons do.

The relay daemon does NOT need to run any other Infernet role. A
dedicated relay-only node is a valid deployment. It does need an
identity for the Schnorr handshake on behalf of itself, but its
identity is NOT used to gate browser access — anyone can connect.

### 2. Public relay list

The control plane exposes a read-only list of relays advertised in
the last 2 minutes:

```
GET /api/v1/dht/relays
```

Response:

```json
{
  "relays": [
    {
      "pubkey": "<hex>",
      "name": "<provider name>",
      "websocket_url": "wss://relay.example.com/dht",
      "kind": "hyperswarm-dht-relay-v0",
      "last_seen": "<iso8601>",
      "max_connections": 32
    },
    ...
  ]
}
```

Public, cacheable for 60s. The browser playground fetches this on
load and picks `MIN_CORROBORATING_RELAYS` (default 2) at random for
its DHT queries. The `/api/v1/dht/relays` endpoint going down does
NOT brick browsers that have already cached a list; SDK callers
SHOULD persist the most recent list to localStorage.

### 3. Bootstrap fallbacks

A browser MUST try relays in this order:

1. Operator-supplied list (SDK config, query string).
2. localStorage cache from a previous load.
3. `/api/v1/dht/relays` from the control plane.
4. A small set of well-known relays compiled into the SDK as a
   last resort (default empty; operators of large deployments may
   patch in their own).

Browsers that can't reach any relay MUST surface a clear "no DHT
access" error rather than silently failing. The chat playground
specifically: the distributed-mode checkbox MUST stay disabled with
an explicit "Network discovery is unreachable from this browser"
tooltip — not the existing `< MIN_RPC_PEERS` shortfall message,
which would imply we successfully looked.

### 4. Browser DHT API

The SDK MUST expose:

```js
import { browserDhtClient } from '@infernetprotocol/discovery/browser';

const dht = await browserDhtClient({ relays: [...] });
const peers = await dht.peersOnTopic('rpc', 'qwen2.5:72b', {
    timeoutMs: 5_000
});
//  → [{ pubkey, address, topics, lastSeen }, ...]
```

Internally:

1. The SDK opens WebSocket connections to up to
   `MAX_PARALLEL_RELAYS` (default 3) relays from the picked set.
2. For each relay, it issues a topic lookup via
   `@hyperswarm/dht-relay`'s client API.
3. Each result entry is a Hyperswarm peer with a public key and
   reachable address.
4. The SDK MAY then run an Infernet handshake (IPIP-0032 §4)
   against each peer, treating the relay as a transparent transport.
   In v0 of this IPIP browser handshake is OPTIONAL — read-only
   discovery (peer counts, model availability) is the load-bearing
   path. Bidirectional handshakes are deferred to a later IPIP that
   defines a browser-side keypair lifecycle.

### 5. Corroboration

A browser query MUST be considered authoritative only when at least
two independent relays return overlapping results within
`CORROBORATION_TIMEOUT_MS` (default 8_000). Specifically:

- "X of Y relays return a peer with this pubkey on this topic" is
  the unit of belief. If `X >= ceil(Y / 2)` AND `X >= 2`, the peer
  is corroborated.
- A peer that appears on 1 relay only is reported as
  `status: "unverified"` to the caller and SHOULD NOT be counted in
  a `ready` decision (the chat playground SHOULD NOT enable
  distributed mode based on uncorroborated peers).

This protects the most likely attack: a single malicious relay
inventing peers to manipulate browser-side routing decisions.
Corroboration is cheap because relay peer-list responses are small;
the latency penalty is the slowest of `MIN_CORROBORATING_RELAYS`
relays.

### 6. New capability tier in `/api/v1/rpc/census`

When invoked from a browser SDK that has executed a successful DHT
query, the SDK SHOULD report its DHT view back via:

```
GET /api/v1/rpc/census?model=<id>&dht_corroborated=<int>
```

The control plane MUST treat the `dht_corroborated` query parameter
as advisory only — it does not affect the heartbeat-based count.
A future IPIP MAY make the control-plane census surface a
`dht_corroborated_min` field aggregated from many SDK reports, but
this IPIP does not define that aggregation (Sybil concerns; an
attacker controlling many "browsers" could inflate the count).

### 7. SDK identity (deferred)

The browser SDK does NOT carry a Schnorr identity in v0 of this
IPIP. Browser-side keys are operationally messy (where do they
live? how do they survive a refresh? how does a user prove
continuity?), and answering those questions is a separate
discussion. v0 is read-only: browsers see who's on the DHT but
can't authenticate as anyone. A future IPIP will define ephemeral
in-memory browser keys + an opt-in `localStorage` persistence
mode for power users.

## Rationale

**Why @hyperswarm/dht-relay and not a custom HTTP/SSE bridge?**
Holepunch maintains the relay package; it's the same code paths
Pear / Keet use for browser clients. Writing our own would
re-derive a half-dozen subtle decisions (pong-keepalive cadence,
stream-multiplexing, error normalization) for marginal gain.

**Why corroboration instead of trusting a single relay?**
A relay that lies can ship the chat playground a fake "ready: true"
census, then route the user's signed job request to a colluding
primary. The damage is bounded — IPIP-0033 §3 still fails-closed on
shortfall on the server side — but the user wastes a round trip and
sees a confusing error. Forcing two-relay corroboration cuts the
attack surface dramatically; an attacker would need majority-relay
control to manipulate browser census decisions.

**Why deferred browser identity?**
The chat playground today doesn't need browser-side identity. The
SDK consumer (the chat playground itself) has its own Nostr keypair
flow inside `chat-view.js` for end-to-end encryption (IPIP-0027);
the DHT layer doesn't need a second one. Defer until a use case
forces the question.

**Why is this different from running the relay on the control
plane?** Because the relay IS a DHT participant — running one on
the control plane makes the control plane a load-bearing node in
the DHT, exactly the coupling IPIP-0032 §5 forbids. Operator-run
relays preserve the property that the control plane can go dark
without breaking discovery.

**Why is `dht_corroborated` advisory only on the control plane?**
A naive integration ("trust whatever the SDK reports") opens a
trivial Sybil: an attacker spawns a thousand SDK instances, each
reporting `dht_corroborated: 9999` for their preferred model, and
the control-plane census starts surfacing fake numbers. Treating
the field as informational keeps the control plane's count
trustworthy until a real reputation / rate-limit story exists for
SDK reports.

## Backwards compatibility

- **Daemons without `specs.dht_relay`** keep working — they just
  don't show up in `/api/v1/dht/relays`. Operators self-select
  into running a relay.
- **Browsers** that don't load the new SDK code path keep using
  the heartbeat-based `/api/v1/rpc/census` exclusively. The
  distributed-mode checkbox behavior is unchanged for them.
- **No schema migration** — `specs.dht_relay` is an additive
  optional field whitelisted in `sanitizeSpecs` (a small follow-up
  PR alongside Phase 1 of the IPIP).

## Reference implementation

Sketch only — no PR yet. Lands in three steps after this IPIP is
Active:

1. **Operator side**
   - `apps/cli/commands/relay.js` — new top-level `infernet relay
     start [--port N] [--public-url URL]` command.
   - `packages/discovery/src/relay-server.js` — wraps
     `@hyperswarm/dht-relay`'s server.
   - Heartbeat in `apps/cli/commands/start.js` reads
     `state.dht_relay` and emits `specs.dht_relay`.

2. **Control plane**
   - `apps/web/app/api/v1/dht/relays/route.js` — list endpoint
     (live providers with `specs.dht_relay`, freshness ≤ 2 min,
     `is_public=true`).
   - `apps/web/lib/data/node-api.js` `sanitizeSpecs` whitelist for
     `dht_relay` slot.

3. **Browser SDK**
   - `packages/discovery/src/browser.js` — `browserDhtClient`,
     `peersOnTopic`, corroboration logic.
   - `packages/discovery/package.json` `exports` map adds
     `./browser` entry.
   - Chat playground (`apps/web/app/chat/chat-view.js`) consumes
     it and falls back to `/api/v1/rpc/census` if no relay is
     reachable.

Phasing:

1. **Phase 1:** spec + operator command + relay capability
   advertisement + sanitizer whitelist.
2. **Phase 2:** control-plane list endpoint + minimal browser SDK
   (lookup-only, no corroboration).
3. **Phase 3:** corroboration logic + chat playground integration.
4. **Phase 4:** declare Active when ≥ 3 production relays are live.

## Test plan

**Unit (pure logic).**
- Picking N random relays from an arbitrary list, deterministic
  with a seeded RNG, drops dead entries.
- Corroboration math: 2 of 3 relays agree → corroborated;
  1 of 3 → unverified; 3 of 3 → corroborated; 0 of 3 → no peer
  reported.
- Sanitizer whitelist for `dht_relay` slot — bounds on
  `max_connections`, websocket URL must be `wss://`, version regex.

**Integration (operator-side).**
- Spin up a relay daemon, point a Node-side `@hyperswarm/dht-relay`
  client at it, run a topic lookup, assert results match a
  parallel direct-Hyperswarm query.

**Browser (manual).**
- Load the chat playground against a control plane stopped via
  `pkill node`. Assert the distributed-mode checkbox still works
  when relays are reachable.

## Security considerations

- **Malicious relay forging peers.** Mitigated by §5 corroboration.
  Peers reported by a single relay are surfaced as `unverified`
  and not counted toward `ready`.
- **Malicious relay omitting peers.** A relay can quietly drop
  peers it doesn't like. Same mitigation: cross-relay
  corroboration. A peer that exists in the DHT but is censored by
  one relay still appears in the others.
- **DoS via relay.** A relay can rate-limit connections per source
  IP. The IPIP doesn't standardize the policy — operators choose.
- **MITM on `wss://`.** Standard TLS threat model. Relays MUST
  use real certificates (Let's Encrypt etc.); self-signed certs
  break browsers anyway.
- **Browser pubkey enumeration.** v0 has no browser identity, so
  there's nothing to enumerate. When v1 adds identity, the IPIP
  will need a privacy section here.

## Privacy considerations

- **Relay sees every browser query.** A relay operator can log
  which topics every connected browser looks up — i.e. which
  models the user is interested in. Browsers SHOULD rotate
  through the relay set rather than sticking to the same one
  for the whole session. v0 of the SDK MUST randomize relay
  selection per query, not per session.
- **Browser IP exposed to relay.** Standard for any HTTP client.
  Users who want stronger privacy (Tor, VPN) handle that at the
  network layer.
- **No browser pubkey leaks.** Read-only v0 means there's nothing
  to leak.

## Open questions

- Should the public relay list (`/api/v1/dht/relays`) also serve
  static fallback relays from a config file, so the list survives
  a control-plane DB outage? Probably yes; trivial to add.
- `MIN_CORROBORATING_RELAYS = 2` is a guess. With ≥ 5 relays in
  the wild, 3 is probably better. Tune at Phase 4.
- Should the chat UI's "X primary · Y slices live" badge show a
  `(via DHT)` qualifier when the count came from corroborated
  relays? Probably yes — different trust signal.
- WebTransport is more efficient than WebSocket but adoption is
  uneven; HTTP/3 issues persist on some networks. Stay on WebSocket
  for v0; revisit if browser support stabilizes.
