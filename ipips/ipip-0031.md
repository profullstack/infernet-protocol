> **Replaced by [IPIP-0033](./ipip-0033.md).** Petals' upstream library
> has not shipped a release in roughly three years and the `/petals/v3-public`
> swarm has effectively no peers — in practice every distributed-mode
> chat run on the live network resolved to "the proxy node and only the
> proxy node," so no fan-out actually happened. IPIP-0033 replaces the
> Petals path with llama.cpp RPC over Hyperswarm-discovered peers
> (IPIP-0032 topic-keyed swarms). The `petals` topic kind in IPIP-0032
> is removed in the same housekeeping pass.

## Abstract

Promotes the `[x] Distribute across all nodes` checkbox on `/chat`
from scaffolding to a real, working swarm proxy. When a user asks for
a model that no single node can hold (Llama 70B, Qwen 72B, …), the
control plane routes their request through any operator who has joined
the model's Petals swarm. The operator's daemon runs a bundled Petals
client that fans out across the public DHT swarm and streams tokens
back as SSE. Per-token CPR receipts (IPIP-0007) attribute payment to
each layer-holding operator, not just the proxying node.

## Motivation

IPIP-0012 specified federated model hosting via Petals as the
mechanism for serving frontier models nobody can fit on one box. Until
this proposal, that was a paper protocol — `/chat` accepted the
distributed flag but the routing was a stub.

Without IPIP-0031, an operator with 24 GB of VRAM cannot meaningfully
contribute to serving a 70B model, and a user asking for one gets a
"model not available" error even when the global swarm has the model
fully covered.

## Specification

### Daemon side

- `apps/cli/lib/inference/petals-client.py.js` — bundled Python petals
  client. Reads a JSON request from stdin
  (`{ model, messages, max_tokens, temperature }`), uses
  `AutoDistributedModelForCausalLM` to fan out across the public DHT
  swarm, and emits one JSON line per token to stdout. The daemon wraps
  each line into an SSE frame for the requesting client.
- `apps/cli/commands/start.js` — new HTTP route on `$PORT` (default
  8080):
  ```
  POST /v1/petals/inference  →  text/event-stream of token | done | error
  ```
  Spawns the bundled Python script per request, pipes stdin, forwards
  stdout line-by-line as SSE.
- `apps/cli/commands/register.js#gatherCoarseSpecs` — reads
  `~/.infernet/inference/state.json` (written by `infernet inference
  serve`) and attaches `petals_models: [<model>]` to the registered
  specs **iff** the petals server pid is alive. Empty array otherwise.

### Server side

- `sanitizeSpecs` in `apps/web/lib/data/node-api.js` passes through
  `petals_models` (capped 5 entries × 200 chars each) and
  `served_models` (capped 50 × 200) without dropping them. (The
  pre-IPIP-0031 sanitizer silently stripped both.)
- SSE handler `app/api/chat/stream/[jobId]/route.js` grew
  `runPetalsProxy()`: when `job.input_spec.distributed === true`,
  query providers `WHERE specs.petals_models @> [<model>]`, pick one
  at random, POST the chat to its `/v1/petals/inference` endpoint,
  parse the daemon's SSE stream line-by-line, and re-emit
  `token | done | error` frames to the browser. Mirror each token
  into `job_events` for audit + replay.
- Returns an honest `"no Petals server for <model>"` error when the
  swarm is empty for the requested model.

### Operator opt-in

```sh
infernet inference serve \
  --backend petals \
  --model meta-llama/Llama-3.1-70B-Instruct
```

This:

1. Starts a Petals server bound to the operator's GPU memory.
2. Joins the public DHT swarm for the requested model.
3. Writes `~/.infernet/inference/state.json` so the next `register`
   advertises `petals_models = ["meta-llama/Llama-3.1-70B-Instruct"]`.

### Per-layer CPR attribution (IPIP-0007 integration)

The proxying node is not the only operator paid. Per-token receipts
are written for every layer-holding operator advertised in the swarm
metadata, so payouts follow contribution rather than proximity.
Implemented in commit `2cd5cd5`.

## Rationale

Alternatives considered:

1. **Run Petals only client-side in the browser** — would let the user
   join the swarm directly, no proxy needed. Rejected: WebGPU petals
   isn't ready for 70B-class models, and we don't want browsers to
   need a long-lived libp2p connection.
2. **Sticky routing — same operator for the whole conversation** —
   simpler accounting. Rejected: an operator going offline mid-
   conversation kills the chat. Random per-request routing recovers
   gracefully.
3. **HTTP/2 streaming instead of SSE** — would scale better. Rejected
   for now; SSE matches the existing chat stream protocol and the
   browser already supports it natively.

## Backwards compatibility

- Existing `/chat` users see no change unless they tick the
  distributed box. The new SSE frames (`token | done | error`) are a
  superset of the old single-node frames.
- Nodes not running `infernet inference serve --backend petals` never
  advertise `petals_models` and are never selected for swarm proxying.
- Sanitizer change is pass-through only — no new validation can reject
  a payload that previously succeeded.

## Test plan

- Unit: `tests/petals-engine.test.js` mocks the bundled Python client
  and asserts SSE frames pass through unchanged.
- Integration: stand up one operator running `inference serve --backend
  petals --model meta-llama/Llama-3.1-70B-Instruct`, then submit a
  distributed chat from the dashboard. Confirm `job_events` contains
  the streamed tokens and a `done` event with usage attached.
- Negative: ask for a model with no swarm presence. Expect a clean
  `"no Petals server for <model>"` error frame, not a hang or 500.

## Security considerations

- The proxying daemon is an unauthenticated relay for arbitrary
  prompts. Mitigations: the Python client runs in a subprocess with
  no filesystem write access outside `~/.infernet/inference/`, and the
  daemon enforces the same per-IP rate limits as inbound chat.
- A malicious operator can MITM the prompt or the response stream.
  IPIP-0027 (NIP-44 ECDH) and IPIP-0028 (multi-party model keys) plug
  this gap when end-to-end encryption is enabled; without them, the
  proxying operator sees plaintext, same as any other inference
  provider today.

## Privacy considerations

The control plane logs which operator was selected to proxy each
distributed chat and persists tokens in `job_events` for audit. This
matches existing chat logging — no additional linkability beyond what
IPIP-0009 / IPIP-0024 already imply.

## Open questions

- Should we cap fan-out so a single operator can't be overwhelmed by
  parallel distributed-chat requests? Today we rely on the daemon's
  built-in concurrency.
- Health-check loop for stale `petals_models` advertisements when the
  Petals server crashes between heartbeats — currently a clean
  restart re-syncs, but a hung process could advertise a model it
  can't actually serve.
