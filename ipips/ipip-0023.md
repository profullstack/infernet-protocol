## Abstract

Adds `infernet train`, `infernet dataset`, and `infernet eval` command
families, a training job lifecycle on the control plane, a provider
training runner, pluggable runtime adapters (microgpt, transformers,
trl, axolotl, unsloth), and a run-wiki artifact system that persists
reproducible training records alongside every job. Also introduces
workload classes C1–C4 and D1–D4 for single-provider, sweep,
async-distributed, and mega-model workloads. Experimental
mega-model and federated-training paths are gated behind
`--experimental` until proven at scale.

See [docs/prds/infernet-train-prd.md](../docs/prds/infernet-train-prd.md)
for full product requirements.

## Motivation

Infernet currently handles inference workloads only. The next
monetization surface — and the strongest differentiator against
bare cloud GPU rental — is practical model improvement: LoRA /
QLoRA fine-tunes, hyperparameter sweeps, evals, distillation, and
eventually federated / async distributed training.

Three converging forces make this the right time:

1. **LoRA/QLoRA democratized fine-tuning.** A single 24 GB GPU
   can fine-tune a 7B model in hours for under $5. Infernet
   providers already have the hardware; they just need a
   standardized job format to accept training work.

2. **Reproducibility is unsolved.** Most practitioners lose their
   hyperparameters, dataset hashes, eval results, and checkpoint
   lineage between runs. The run-wiki pattern (persistent markdown
   + JSONL artifacts per job) fixes this at the infrastructure
   layer, not as a convention.

3. **Mega-model inference and distributed training are becoming
   economically viable on heterogeneous hardware.** Infernet's
   async/federated approach — where peers exchange compressed
   deltas rather than tight-sync all-reduce — lets the protocol
   operate across real-internet WAN connections that datacenter
   training assumes away.

The `packages/training` package already exists with deepspeed,
opendiloco, openrlhf, petals, and stub backends behind the
`createTrainer()` interface. This IPIP wires those backends to
the CLI, control plane, and provider daemon, and adds the
production-grade runtime adapters and job lifecycle that turns
the scaffold into a shipping feature.

## Specification

### 1. Workload Classes

Infernet extends its workload class model. Classes A and B are
existing inference workloads; this IPIP defines C and D.

| Class | Name | Sync requirement | v0.1 |
|---|---|---|---|
| C1 | Single-provider training | None (one box) | MUST ship |
| C2 | Sweep training | None (embarrassingly parallel) | MUST ship |
| C3 | Async distributed training | Async delta exchange | Experimental |
| C4 | Cross-provider tight-sync training | Low-latency fabric | NOT v0.1 |
| D1 | Mega-model inference | Replicas / shards | Roadmap stub |
| D2 | Distributed adapter training | Async/federated | Experimental |
| D3 | MoE/routed expert training | Async | Research |
| D4 | Dense decentralized pretraining | Synchronous all-reduce | Research only |

Implementations MUST reject C4/D4 workloads in v0.1 with:
`error: workload class C4/D4 requires --experimental and is not
supported in this release`.

### 2. CLI Commands

#### 2.1 `infernet train`

```
infernet train start [--config <file>] [--base-model <id>]
                     [--dataset <path>] [--method lora|qlora|full]
                     [--runtime <name>] [--local] [--output <dir>]
infernet train estimate --base-model <id> --dataset <path>
                        [--method <m>] [--max-price-usd <n>]
infernet train list
infernet train status <job_id>
infernet train logs <job_id> [--follow]
infernet train metrics <job_id>
infernet train cancel <job_id>
infernet train resume <job_id>
infernet train artifacts <job_id>
infernet train download <job_id> [--output <dir>]
infernet train topology <job_id>         # stub in v0.1
infernet train verify <job_id>           # stub in v0.1
infernet train adapter-distributed ...  --experimental
infernet train pretrain ...             --experimental
```

`infernet train start --local` MUST run the job in-process on the
operator's machine using the specified runtime, without contacting
the control plane. This is the primary path for Milestone 2.

`infernet train estimate` MUST work without network access and
without a config file. It MUST print a human-readable summary to
stdout and exit 0.

`--experimental` flag MUST be present for adapter-distributed and
pretrain subcommands; the CLI MUST print a prominent warning before
proceeding:

```
WARNING: This command uses an experimental training strategy.
Results may be non-deterministic, incomplete, or incorrect.
Do not use for production workloads without validation.
```

#### 2.2 `infernet dataset`

```
infernet dataset validate <path> [--format chatml|alpaca|sharegpt|text]
infernet dataset stats <path>
infernet dataset split <path> [--validation <f>] [--test <f>]
infernet dataset upload <path> --name <name>
infernet dataset list
infernet dataset remove <dataset_id>
```

`validate` MUST detect the format automatically when `--format` is
omitted, and MUST report: row count, detected format, any
malformed rows (with line numbers), and whether the file is suitable
for training.

`stats` MUST report: row count, token count estimate, min/max/mean
sequence length, and top-10 length distribution percentiles.

#### 2.3 `infernet eval`

```
infernet eval start --model <path_or_id> --dataset <path>
                    [--tasks perplexity,chat-regression,json-validity]
infernet eval report <eval_id>
```

`eval start --local` runs entirely in-process. Remote eval is a
Milestone 3+ feature.

### 3. Config Schema

`infernet.train.yml` MUST support at minimum:

```yaml
name: string                     # human label for the run
base_model: string               # HF model id or local path
method: lora | qlora | full      # training method
runtime: microgpt | transformers | trl | axolotl | unsloth
workload_class: C1 | C2 | C3

input:
  dataset: string                # path or dataset_id
  format: chatml | alpaca | sharegpt | text
  validation_split: float        # 0–1

training:
  epochs: int
  learning_rate: float
  batch_size: int
  gradient_accumulation_steps: int
  max_seq_len: int
  seed: int

lora:                            # required when method is lora or qlora
  rank: int
  alpha: int
  dropout: float
  target_modules: string[]

resources:
  min_vram_gb: int
  preferred_vram_gb: int
  max_runtime_hours: int
  max_price_usd: float
  allow_preemptible: bool

outputs:
  artifact_store: local | s3 | infernet
  download: string               # local path
  publish_model_card: bool
```

Unknown top-level keys MUST be preserved and passed through to the
runtime adapter via `config.extra`. This allows runtime-specific
extensions without schema drift.

### 4. Runtime Adapter Interface

Each runtime lives in `packages/training-runtimes/src/runtimes/`.
The interface is:

```js
export class TrainingRuntime {
  get name() { return 'runtime-name'; }

  // Return null if config is valid, or an array of error strings.
  async validateConfig(config, context) {}

  // Return an EstimateResult: { vram_gb, disk_gb, runtime_range_hrs,
  // cost_range_usd, token_count, row_count, compatible_providers }.
  async estimate(config, context) {}

  // Prepare local workspace dir for the job.
  async prepareWorkspace(config, context) {}

  // Return a Docker container spec object (image, cmd, env, mounts,
  // limits). Used by the provider runner.
  async buildContainerSpec(config, context) {}

  // Parse a stdout line from the training process.
  // Return a metrics object or null if the line is not a metrics line.
  async parseMetrics(line, context) {}

  // Collect artifacts from the workspace into context.artifactsDir.
  // Called after training completes.
  async collectArtifacts(workspace, context) {}
}
```

All methods are optional; a runtime that does not implement a method
inherits a no-op or error default from the base class. Runtimes
MUST NOT throw on unknown config keys.

`microgpt` runtime MUST:
- Run entirely on CPU with no external pip installs in CI.
- Complete in under 2 minutes on a standard CI runner.
- Emit metrics lines parseable by `parseMetrics`.
- Produce at minimum: a checkpoint file, a generated sample, and
  `metrics.jsonl`.

All other v0.1 runtimes (`transformers`, `trl`, `axolotl`,
`unsloth`, `max`) MAY be stubs that return a "not implemented"
error from `prepareWorkspace` with a helpful message pointing to
the install guide.

### 5. Run Wiki Artifact Structure

Every completed local or remote training job MUST produce the
following artifact tree under `<output_dir>/`:

```
README.md          # human summary: job id, model, method, result
config.yml         # exact config used (post-resolution)
metrics.jsonl      # one JSON object per training step
events.jsonl       # lifecycle events (started, checkpoint, done, error)
model-card.md      # HF-style model card
dataset-card.md    # dataset provenance, format, splits, sha256
eval-report.md     # eval results if eval was run; placeholder otherwise
logs/
  train.log        # raw stdout/stderr from runtime
artifacts/
  <runtime-specific files>
```

`README.md` MUST include: job id, base model, method, runtime,
dataset name + sha256, epoch count, final loss, duration, provider
(or "local"), and a reproduction command.

`model-card.md` MUST follow the Hugging Face model card schema at
minimum for: base_model, tags, license, training_procedure, and
limitations.

`metrics.jsonl` MUST be append-only. Each line MUST be valid JSON
with at minimum: `{ "step": int, "loss": float, "ts": iso8601 }`.

`runs/index.md` and `runs/log.md` MUST be maintained at the
configured output root (default `./runs/`). `log.md` is
append-only; a new entry MUST be added when a job starts and when
it completes.

`POST /api/v1/train/jobs` accepts the `training_jobs` fields in the
request body. Response MUST include the assigned `id` and `status`.

`GET /api/v1/provider/training/jobs/poll` returns at most one job
in `queued` state that matches the polling provider's capabilities.
It MUST NOT return jobs already assigned or in a terminal state.
SHOULD return 204 when no matching job is available.

`POST /api/v1/provider/training/jobs/:id/claim` transitions the job
from `queued` to `assigned`. MUST be idempotent if the same provider
re-claims the same job (returns 200 with current state). MUST return
409 if another provider claimed it first.

### 8. Provider Training Capability Advertisement

Providers extend their heartbeat payload (IPIP-0009 §3.1) with:

```json
{
  "training": {
    "supports_training": true,
    "runtimes": ["microgpt", "transformers"],
    "cuda": "12.4",
    "rocm": null,
    "vram_gb": 48,
    "disk_free_gb": 800,
    "max_job_hours": 12,
    "container_runtime": "docker",
    "network_policy": "outbound-only",
    "preemptible": false,
    "supports_large_model_inference": false,
    "supports_adapter_training": true,
    "supports_async_federated": false,
    "network": {
      "region": "us-west",
      "estimated_down_mbps": 950,
      "estimated_up_mbps": 850,
      "nat_type": "public"
    }
  }
}
```

The `training` key is optional. Providers that do not include it
MUST NOT receive training jobs.

Providers configure training capability via:

```bash
infernet train provider enable \
  --runtimes microgpt,transformers \
  --max-job-hours 12 \
  --ephemeral-disk-gb 500
```

This writes to the local config and registers the capability with
the control plane on next heartbeat.

### 9. Security Requirements

Training jobs MUST run inside containers. All of the following are
REQUIRED for any provider that accepts training jobs:

- Container MUST have no access to host secrets or host network
  interfaces beyond outbound HTTPS.
- Job workspace MUST be a unique per-job random path under a
  controlled base dir (e.g. `/var/infernet/jobs/<uuid>/`).
- Container MUST be subject to disk quota, memory limit, CPU quota,
  and max-runtime enforcement.
- Dataset and artifact files MUST be SHA-256 verified before use
  and before upload.
- Training logs MUST be scanned for known secret patterns (API
  keys, tokens, private keys) before being forwarded to the control
  plane. Matching lines MUST be redacted.
- Providers MUST NOT accept private-dataset jobs unless
  `allows_private_datasets = true` is set in their capability
  config.
- Container images MUST come from an allowlist maintained by the
  runtime adapter. Arbitrary images are not permitted in v0.1.

### 10. Estimation Algorithm

`infernet train estimate` MUST produce a `EstimateResult` using
the following algorithm (all values are approximate and MUST be
labeled as such in CLI output):

1. **Token count** = `row_count × mean_seq_len`. If the dataset
   file is available locally, compute `mean_seq_len` from a sample
   of the first 100 rows. Otherwise use 256 as the default.

2. **VRAM floor** = base model parameter GB × method multiplier:
   - `full`: 2.0× (gradients + optimizer state)
   - `lora`: 0.7× (adapter only + frozen base)
   - `qlora`: 0.4× (quantized base + adapter)

3. **Runtime range** = `(token_count / throughput_low, token_count /
   throughput_high)` where `throughput_low = 500 tok/s` and
   `throughput_high = 2000 tok/s` are conservative defaults.
   Multiply by `epochs`.

4. **Cost range** = runtime range × `(price_low, price_high)` where
   defaults are `$0.20/GPU-hr` (low) and `$1.50/GPU-hr` (high).

CLI output MUST include the warning:
```
WARNING: Estimate is approximate. Actual results vary by GPU, 
dataset length distribution, model cache state, and provider load.
```

## Rationale

**Why plug into `packages/training` instead of a new package?**
The scaffold is already there with the right interface shape. Adding
new runtime adapters and CLI wiring to it avoids a second training
abstraction in the repo.

**Why microgpt as the CI reference trainer?** Karpathy's microgpt
is ~300 lines of dependency-free Python that runs on CPU in under
90 seconds on minimal hardware. It proves the complete training
lifecycle (forward pass, backward pass, checkpoint, sample
generation) without requiring GPU, CUDA, PyTorch >2.x, or
internet access. No other trainer meets all four constraints.

**Why run-wiki artifacts instead of just a database?** Run records
in a database are ephemeral — they depend on a running Supabase
instance, a network connection, and the control plane being up.
Markdown + JSONL files on disk are permanent, portable, and
readable with any text editor. The database is for query and
coordination; the wiki is the source of truth for reproducibility.

**Why stub experimental commands in v0.1 instead of skipping them?**
A CLI that returns a clear `not yet supported` message with a link
to the roadmap is better product design than a CLI that returns
`command not found`. Stubs let users discover the surface without
marketing promises.

**Why require `--experimental` instead of just documenting caveats?**
Operators running production workloads should not accidentally opt
into research-grade training strategies. Requiring an explicit flag
is a speed bump that distinguishes exploratory use from operational
use at the command line, not just in the docs.

**Why not implement tight-sync all-reduce (C4) at all in v0.1?**
The networking primitives for reliable low-latency gradient
synchronization across public P2P peers do not exist in this
protocol yet. Pretending otherwise by shipping a broken C4
implementation would undermine trust in the classes that do work.

**Relationship to existing `packages/training` backends.** The
`deepspeed`, `openrlhf`, `opendiloco`, and `petals` backends
already exist as stubs. IPIP-0023 adds a separate
`packages/training-runtimes` layer with the concrete job-lifecycle
runtime adapters. The distinction: `packages/training` is the
distributed-coordination layer (how peers synchronize); 
`packages/training-runtimes` is the per-node execution layer
(which Python trainer runs inside the container).

## Backwards compatibility

This IPIP is entirely additive:

- No existing CLI commands change.
- No existing DB tables change (new tables only).
- No existing API routes change (new routes only).
- The heartbeat payload gains an optional `training` key; existing
  nodes that don't include it are unaffected.
- The `packages/training` index is extended with new backends; the
  existing `createTrainer()` interface and auto-select logic are
  unchanged.

Providers that do not opt in via `infernet train provider enable`
will never receive training jobs.

## Security considerations

Training jobs introduce a new attack surface absent from inference:

- **Arbitrary code execution.** A malicious dataset or config could
  trick a runtime into executing attacker-controlled Python. Mitigated
  by container sandboxing, no-host-secrets policy, and allowlisted
  images.
- **Data exfiltration.** Long-running training containers have more
  opportunity to exfiltrate data over outbound HTTPS. Mitigated by
  container network policy (outbound HTTPS only) and log scanning.
- **Artifact poisoning.** A malicious provider could return corrupt
  or backdoored model weights. Mitigated by SHA-256 artifact
  verification and, later, spot-check evals.
- **DoS via resource exhaustion.** A job that requests more VRAM or
  disk than advertised could destabilize the provider host. Mitigated
  by container resource limits enforced by the provider runner.
- **Log injection.** A training script could write fake metric lines
  or fake completion events to stdout. Mitigated by signed event
  envelopes on the control-plane reporting path (not local stdout).

Private-dataset jobs require explicit provider opt-in because they
expose the provider to content they did not consent to process.

## Privacy considerations

- Training datasets may contain PII. Infernet does not inspect
  dataset content beyond format validation and SHA-256. Operators
  are responsible for dataset compliance.
- Provider training capability advertisement (§8) adds hardware
  details (vram_gb, disk_free_gb, cuda version) to the heartbeat.
  These are equivalent in sensitivity to the existing GPU spec
  fields and covered by the same `--no-advertise` opt-out.
- `model-card.md` records the dataset name and sha256 as provenance.
  If the dataset name is sensitive, operators MUST use a
  non-identifying name when uploading via `infernet dataset upload`.
- Run-wiki files are written to the operator's local filesystem
  only unless `artifact_store: infernet` is set. Remote artifact
  storage is subject to the artifact store's privacy terms.

## Open questions

- Should private datasets be supported in v0.1 or only
  local/self-hosted? Lean: local only for v0.1; remote private
  datasets require encrypted transit and provider consent UI.
- Should artifact storage default to `local` or `infernet`?
  Lean: `local` for v0.1 to avoid depending on the artifact
  store being live.
- Should payment escrow reserve `max_price_usd` before a job starts?
  Lean: yes for remote jobs to prevent underpayment disputes.
- Should providers be paid for jobs they fail or that are preempted?
  Lean: partial payment proportional to steps completed and
  checkpoints uploaded, once the checkpoint system is live.
- Should `infernet train start` support HF auth tokens for gated
  models, and if so how are they passed to the container without
  the provider seeing them? Lean: encrypted one-time secret, not
  a plain env var — design in Milestone 5.
