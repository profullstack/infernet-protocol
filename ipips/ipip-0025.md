## Abstract

**Phase 1 (shipped):** Encrypts conversation content
(user prompts, assistant responses, and streaming token chunks) stored
in Supabase using AES-256-GCM with a server-side key
(`INFERNET_DB_ENCRYPTION_KEY`). Supabase stores ciphertext only;
plaintext exists solely in the Next.js process. A credential leak of
the Supabase service-role key no longer exposes conversation content.

**Phase 2 (future):** Removes conversation content from Supabase
entirely. Messages are held in a short-lived server-side cache; providers
fetch them directly from the control plane. Supabase never stores prompt
or response content even in encrypted form.

A companion migration adds auto-expiry of job_events rows and a
cleanup of the content fields from the jobs table after job completion
as a defence-in-depth measure and a path for operators running the
current schema while this IPIP is being implemented.

## Motivation

The current architecture stores the following in Supabase in plaintext:

| Table | Column | Content |
|---|---|---|
| `jobs` | `title` | First 80 chars of the user prompt |
| `jobs` | `input_spec` | Full conversation history `{messages:[{role,content}...]}` |
| `jobs` | `result` | Full assistant response |
| `job_events` | `data` | Every token chunk during streaming |

This creates several problems:

1. **Supabase as a data processor.** Any Supabase employee, a
   breached credential, or a misconfigured RLS policy can read
   every conversation the platform has ever processed. Users of
   the public playground have no reasonable expectation that
   their prompts persist indefinitely in a third-party database.

2. **Incompatibility with client-side encryption.** Users
   reasonably expect that "end-to-end" GPU compute means the
   platform operator cannot read their prompts. Storing plaintext
   content in Supabase violates that expectation regardless of
   transport encryption.

3. **Content is only needed transiently.** The provider needs
   the messages for the duration of inference (~seconds). The
   SSE client needs token events for the duration of streaming
   (~seconds). Neither use case requires indefinite persistence.

4. **True client-side encryption is architecturally blocked by
   the current design.** Providers poll Supabase for jobs and
   read `input_spec.messages` directly. If we encrypt before
   insertion, providers cannot decrypt. The fix is architectural:
   remove content from the DB, not add encryption layers on top
   of a design that puts content in the DB by necessity.

## Specification

### 1. Server-side message cache

Add a module `apps/web/lib/job-input-cache.js`:

```js
// In-process TTL cache: jobId → { messages, model, maxTokens,
// temperature, expiresAt }. Entries are evicted when the job
// completes or after JOB_INPUT_TTL_MS, whichever is first.
const JOB_INPUT_TTL_MS = 5 * 60 * 1000; // 5 minutes
```

The cache MUST be a `Map` keyed by job UUID. Each entry MUST
include an `expiresAt` timestamp. A background interval (every
60 s) MUST evict stale entries so abandoned jobs don't accumulate.

The cache is in-process. In a multi-replica deployment, all
replicas share the Supabase Postgres row to find the assigned
provider, so the provider contacts the same replica that holds the
cache entry. If a round-robin load balancer routes the provider to
a different replica, the provider's `GET /api/v1/node/jobs/:id/input`
call returns 404, at which point the server should re-create the
entry from the `jobs` row if `input_spec` is still set, or return
an error. Multi-replica deployments SHOULD use sticky sessions for
the provider-side `/api/v1/node/` routes, or SHOULD migrate to a
shared in-process cache (e.g. Redis) when they reach that scale.

### 2. Changes to `createChatJob`

`createChatJob` MUST:

1. Store the job in `jobs` WITHOUT `messages` in `input_spec`:
   ```js
   input_spec: {
     max_tokens: maxTokens,
     temperature,
     ...(nimAvailable ? { fallback: "nvidia-nim" } : {})
     // messages are NOT stored here
   }
   ```

2. Write messages to the job-input cache:
   ```js
   jobInputCache.set(job.id, { messages, modelName, maxTokens, temperature });
   ```

### 3. New provider endpoint: `GET /api/v1/node/jobs/:id/input`

This endpoint MUST:
- Require a valid `X-Infernet-Auth` signed request (IPIP-0003).
- Verify the requesting provider is the assigned provider for
  the job (check `jobs.provider_id` matches the calling pubkey's
  provider row).
- Return the cached input once and evict the cache entry
  (`delete`):
  ```json
  { "messages": [...], "modelName": "...", "maxTokens": 512, "temperature": 0.7 }
  ```
- Return 404 if the cache entry has expired or been consumed.
- Return 403 if the requesting provider is not the assigned one.

The one-time-read semantics mean the cache entry is deleted on
first successful fetch. If the provider crashes before completing
the job and a retry is needed, the control plane MUST re-create
the entry (see §6, Checkpoint recovery).

### 4. Provider daemon changes

The provider daemon's job polling loop currently reads
`input_spec.messages` from the polled job row. After this IPIP:

1. The daemon polls for available jobs (existing).
2. When a job is claimed, the daemon calls
   `GET /api/v1/node/jobs/:id/input` to fetch messages.
3. Inference runs as today.

If `/input` returns 404, the daemon MUST mark the job as failed
with error `"input expired — job must be resubmitted"` and the
control plane MUST mark the job `failed` so the client can retry.

### 5. NIM fallback path

The SSE stream route (`/api/chat/stream/:id`) currently reads
`job.input_spec.messages` from Supabase for the NIM path. After
this IPIP, it MUST read from the job-input cache instead:

```js
const input = jobInputCache.get(jobId) ?? {};
```

If the cache entry is missing (e.g. the request arrived after
TTL expiry), the route MUST return an error event:
`"input expired — please retry"`.

Because the NIM path runs in the same process that created the
job, the cache entry will always be present if the request is
handled promptly. The 5-minute TTL covers all realistic cases.

### 6. Checkpoint recovery for provider retries (future)

When checkpoint resume is implemented (IPIP-0023 Milestone 5),
the provider will need to re-fetch input on resume. The cache
entry will have been evicted after first read. Two options:

a. Store an encrypted copy of `input_spec.messages` using the
   provider's Nostr pubkey as the encryption key. Only that
   provider can decrypt. This is the true client-side encryption
   path for the retry case.
b. Require the client to resubmit the job from the application
   layer.

Option (b) is simpler. Option (a) is specified here as the
long-term direction but is not required by this IPIP.

### 7. Changes to `jobs` table: clear content after completion

Add a Supabase migration that:

a. Adds a `GENERATED ALWAYS` column or uses a trigger to clear
   `input_spec` and `result` from `jobs` when `status` transitions
   to `completed`, `failed`, or `cancelled`. Operators who need
   audit trails SHOULD use application-layer logging outside
   Supabase.

b. Sets a retention policy on `job_events`: a pg_cron job or
   Supabase scheduled Edge Function deletes `job_events` rows
   older than 1 hour.

This migration applies to all operators regardless of whether
they have deployed the §2–§5 changes. It is the "defence in
depth" layer.

### 8. `jobs.title` field

`jobs.title` currently stores the first 80 characters of the
user prompt for the operator dashboard. After this IPIP:

- `title` MUST be set to a non-content placeholder such as
  `"chat"` or the model name (e.g. `"qwen2.5:7b"`).
- The full prompt MUST NOT appear in this field.

The operator dashboard SHOULD display `model_name + timestamp`
as the job label instead of a prompt excerpt.

### 9. `job_events.data` for token events

Under the new architecture, `job_events` is still used for the
P2P Realtime streaming path (provider writes tokens; SSE route
tails them via Realtime). This table still contains token chunks
during the streaming window.

The §7 migration (1-hour TTL cleanup) covers this. Operators who
want zero Supabase content exposure SHOULD additionally enable the
§5 NIM path to bypass `job_events` for the NIM fallback (NIM
tokens go directly to the SSE client without being stored).

Long-term, the P2P streaming path should move to a direct
provider-to-web-app HTTP stream rather than going through Supabase
Realtime. That is a separate IPIP (deferred; requires NAT
traversal work from IPIP-0006).

## Rationale

**Why not client-side encryption with provider decryption?** For
a browser to encrypt with a key that only the provider can decrypt,
the browser needs the provider's public key before sending the
request. That requires an extra round-trip and the provider's
public key to be trusted by the client. More importantly, the
provider's Nostr keypair is already public — its `npub` is
advertised in the heartbeat. Encrypting to the provider's pubkey
is technically feasible, but the current provider polling model
(provider reads from Supabase) means the ciphertext must still
pass through Supabase. We'd be encrypting content that Supabase
can correlate by metadata anyway (job ID, IP, timestamp). The
architectural clean break is to not store content in Supabase at
all, which is what §2–§5 achieve.

**Why an in-process cache instead of a separate KV store?** For
v1, a single control-plane replica is the common deployment. An
in-process Map is zero-dependency, fast, and sufficient. The
migration path to Redis is clear and documented in §1.

**Why one-time-read on `/input`?** The message content is only
needed once (at inference time). One-time-read minimises the
exposure window and makes it auditable — if a provider fetches
input twice, something is wrong.

**Why not simply skip storing messages altogether and pass them
directly in the polling response?** The polling endpoint
(`GET /api/v1/node/jobs/poll`) returns many jobs for matching
purposes. Embedding messages in the poll response would leak
messages to providers that end up not claiming the job. The
separate `/input` endpoint scoped to the assigned provider avoids
this.

## Backwards compatibility

**Providers running old daemons** will try to read
`input_spec.messages` from the polled job row. After this IPIP,
that field will be empty. Old daemons will fail the job. This is
a **breaking change for old provider daemons**. Providers MUST
upgrade before the control plane deploys this change. The release
notes MUST call this out explicitly.

**Migration plan for staged rollout:**
1. Deploy the §7 migration (TTL cleanup, clear on completion) —
   backwards-compatible, deploy independently.
2. Deploy the `/input` endpoint and cache on the control plane.
3. Deploy the daemon change (fetch `/input` on claim).
4. Remove `messages` from `createChatJob`.
5. In a follow-up migration, `DROP` the `input_spec` column or
   narrow it to non-content metadata.

## Test plan

### Unit

- `job-input-cache.js`: set/get/delete/expiry. Verify eviction
  interval removes stale entries.
- `createChatJob` with new path: verify `input_spec` in the
  inserted row contains NO `messages` key.
- `/input` endpoint: 200 on first call, 404 on second call,
  403 for wrong provider, 404 after TTL.

### Integration

- Full P2P chat job: verify `job_events` rows are deleted after
  1 hour (mock pg_cron or run cleanup manually).
- Verify `jobs.input_spec` contains no messages after job
  completes.
- Verify `jobs.title` is `"chat"` or model name, not prompt text.

### E2E regression

Existing chat tests must continue to pass. The golden path
(send message → receive tokens → done) is unchanged from the
user's perspective.

## Security considerations

- The job-input cache is in-process memory. Process restart (e.g.
  a deploy mid-job) evicts all entries. Affected jobs fail with
  "input expired" and clients retry. This is acceptable — the
  alternative (persisting to Supabase) is what we're removing.
- The `/input` endpoint MUST check provider assignment before
  returning content. A provider that guesses a job UUID but is
  not the assigned provider MUST receive 403.
- The one-time-read semantics mean a replay attack (a compromised
  provider trying to re-fetch after the first read) receives 404.
- `job_events` still contains token data during the streaming
  window. The 1-hour TTL migration limits the exposure window.

## Privacy considerations

After this IPIP:
- No user prompt or assistant response is stored in Supabase
  beyond the streaming window (~seconds for P2P, cleared for NIM).
- `jobs.title` contains model name only, not prompt content.
- `job_events` is deleted within 1 hour of creation.
- The control-plane operator can read messages in-process (they
  pass through the Next.js server). This is unavoidable given
  the routing architecture; the threat model is Supabase-as-third-
  party, not operator-as-adversary.
- Self-hosted operators who run their own Next.js + Supabase
  instance never expose content to Supabase Cloud at all —
  Supabase is local to their stack.

## Open questions

- Should the dashboard show a privacy notice on `/chat` that
  explains the TTL policy and the in-process-only model?
- When provider retries are implemented (checkpoint resume,
  IPIP-0023 §6), should we re-encrypt messages to the provider's
  pubkey for storage, or require client resubmit?
- Should the `/input` endpoint support a `claim + fetch` atomic
  operation to close the race between claim and fetch?
