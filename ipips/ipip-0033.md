## Abstract

Replaces IPIP-0031 (Petals) as Infernet's federated-inference backend.
Operators that opt into hosting a slice of a too-large-for-one-box model
run llama.cpp's `rpc-server`. Discovery is via the Hyperswarm DHT
(IPIP-0032) on the topic key
`sha256("infernet:v1:rpc:<canonical_model_id>")`. A consumer that
checks "Distribute across all nodes" on `/chat` reaches a control-plane
proxy that picks a primary `llama-server` host, hands it an `--rpc
host:port,...` list of currently-announced peers, and streams the
resulting tokens back as SSE. Per-token CPR receipts (IPIP-0007) split
payment across the contributing RPC hosts by allocated layer share —
the same accounting shape IPIP-0031 used, just over a backend that
actually fans out.

## Motivation

IPIP-0031 specified Petals. In practice, when distributed mode shipped
on the live network, every chat that picked the Petals path resolved
to "the proxy node and only the proxy node" — `chosen_servers` was
either empty or contained only the proxy's own libp2p peer id. The
underlying causes are structural:

- Petals' upstream library hasn't shipped a release in ~3 years; its
  primary backer (Together AI) pivoted to commercial APIs.
- Petals' default DHT prefix is `/petals/v3-public`, a swarm with
  effectively no live peers. We never ran an Infernet-private subnet,
  so Infernet operators don't actually find each other through it.
- Petals' model ecosystem (HuggingFace-quantized transformers) is
  divergent from where Infernet operators already live (GGUF / Ollama
  / llama.cpp).

llama.cpp solves all three problems for the audience we have:

1. **Active.** ggerganov/llama.cpp ships releases monthly; the `rpc-server`
   backend has been in tree for over a year and is maintained.
2. **Discovery is solved separately.** IPIP-0032 already specs the
   Hyperswarm DHT we need. Each model gets a topic key, peers find
   each other directly, the control plane stops being a chokepoint.
3. **Native to the stack.** Operators are already running llama.cpp
   under Ollama. Hosting an `rpc-server` for the same GGUF they
   already serve is a one-flag change.

## Specification

### 1. Operator: hosting an RPC slice

A daemon that wants to contribute to a federated model MUST run
`llama.cpp`'s `rpc-server` on a port the daemon advertises. The
daemon's heartbeat (IPIP-0006 §heartbeat) MUST include:

```json
{
  "specs": {
    "rpc": {
      "models":   ["<canonical_model_id>", ...],
      "engine":   "llama.cpp",
      "version":  "<llama.cpp git tag or commit short>",
      "host":     "<advertised host or null when private>",
      "port":     <int>,
      "vram_gb":  <int>,            // free VRAM offered to RPC clients
      "ram_gb":   <int>,            // free RAM offered to RPC clients
      "max_concurrent": <int>       // number of concurrent RPC clients
    }
  }
}
```

`models` is the canonical (NFC-normalized, lowercased) model id —
identical to the IPIP-0032 `model` topic value. The daemon MUST join
the `rpc:<model>` Hyperswarm topic for every model in `rpc.models`
with `server: true` when `is_public=true`, `server: false` (lookup
only) otherwise. The daemon MAY simultaneously serve the same model
under the existing `model:<id>` topic for non-distributed routing.

The daemon SHOULD NOT advertise an `rpc.models` entry it cannot
actually serve at the requested time — joining is a public claim of
capability. A heartbeat with no `rpc.models` (or an empty array) MUST
be treated by the control plane as "this node is no longer offering
RPC slices."

### 2. Operator: hosting the primary `llama-server`

A daemon MAY also volunteer to be the primary entry point — the host
that runs `llama-server` itself and orchestrates the chosen RPC peers.
This is a different role and a different capability advertisement:

```json
{
  "specs": {
    "rpc_primary": {
      "models":  ["<canonical_model_id>", ...],
      "engine":  "llama.cpp",
      "version": "<llama.cpp git tag or commit short>"
    }
  }
}
```

A node MAY be both an RPC slice provider AND a primary; the two roles
are independent. A node that is ONLY a primary still announces on the
`rpc:<model>` topic but with `server: true, client: true` — primaries
are the side that does discovery + dial-out, so they need to find
slices.

### 3. Control plane: routing a distributed job

When a chat is submitted with `distributed: true`, the control plane:

1. Looks up `model_id` against the live providers list, filtering on
   `specs.rpc_primary.models` to find primary candidates. Picks one
   reputation-weighted (existing helper, IPIP-0019 §scheduler).
2. Looks up RPC slice candidates: providers with `model_id` in
   `specs.rpc.models`, freshness ≤ `2 * heartbeat_interval`, status
   `available`, NOT in `private` trust tier (IPIP-0026 §2.1).
3. Builds the `--rpc` list: `host1:port1,host2:port2,...`, capped at
   `MAX_RPC_PEERS` (default `8`). The set MUST exclude the primary
   itself unless `rpc.models` contains the model and the primary
   advertises slack capacity.
4. POSTs to the primary's `/v1/rpc/inference` with body:
   ```json
   {
     "model": "<canonical_model_id>",
     "messages": [...],
     "max_tokens": ...,
     "temperature": ...,
     "rpc_peers": [
       { "host": "1.2.3.4", "port": 50052, "pubkey": "<hex>" },
       ...
     ]
   }
   ```
5. Proxies the resulting SSE stream back to the consumer (same shape
   as the IPIP-0031 proxy: `meta` → `routing` → `token` × N → `done`).

If fewer than `MIN_RPC_PEERS` (default `2`) RPC slices are available
for the requested model, the control plane MUST refuse the
distributed-mode request with a 503 + a structured body explaining the
shortfall — it MUST NOT silently fall back to single-node inference,
because that's what made IPIP-0031 misleading.

### 4. Daemon: serving `/v1/rpc/inference`

A primary daemon receiving `/v1/rpc/inference`:

1. Validates that `rpc_peers[].pubkey` are all live in the daemon's
   own peer cache (it learned them from the Hyperswarm `rpc:<model>`
   topic) — drops any pubkey it has not seen handshake for in the
   last `RPC_PEER_FRESHNESS_MS` (default 5 minutes).
2. Spawns `llama-server` with:
   ```
   llama-server --model <gguf_path> \
                --rpc <host1:port1,host2:port2,...> \
                --gpu-layers <auto> \
                ...
   ```
   The `--gpu-layers` value is the daemon's choice; it SHOULD distribute
   layer placement so that the primary keeps embedding + final layers
   locally and farms middle layers out to RPC peers (this is
   llama.cpp's default behavior; the spec doesn't override it).
3. Streams `llama-server`'s output tokens back as SSE. Emits a
   `routing` SSE frame at first token containing the actual
   per-peer layer assignments llama.cpp resolved (it logs these to
   stderr; the daemon parses them out, NOT a freeform structured
   field).
4. On error from `llama-server`, emits `error` and finalizes.

### 5. Routing event format (UI verification)

The `routing` SSE frame the primary emits MUST carry:

```json
{
  "engine": "llama.cpp",
  "version": "<llama.cpp version>",
  "primary": { "pubkey": "...", "name": "...", "host": "..." },
  "peers": [
    {
      "pubkey": "<hex>",
      "name": "<provider name or null>",
      "host": "<addr or null when private>",
      "layers": { "start": 0, "end": 31 },
      "status": "ok" | "stalled" | "dropped"
    },
    ...
  ]
}
```

Distinct from IPIP-0031's Petals shape: `layers` is an explicit range
(not block indices), and each peer has a per-job `status` so the chat
UI can show stalled / dropped peers in the verification panel.

### 6. CPR receipt attribution

Same shape as IPIP-0031 §receipts, with one structural change:

- Total job offer is split across `peers` weighted by `(layers.end -
  layers.start)`.
- The primary receives a base share equal to `1 / (n_peers + 1)`
  before the layer-weighted split, in recognition of orchestration +
  embedding + final-layer compute. Operators can argue about the
  exact constant; this IPIP picks `1 / (n_peers + 1)` as a starting
  point and a future IPIP MAY tune it.

The same `enqueueAndFlush` path used by IPIP-0031's
`emitPetalsReceipts` is reused — only the pubkey-resolution source
changes (heartbeat `specs.rpc.host:port → pubkey` instead of
`specs.petals_peer_id`).

### 7. Trust tier interaction (IPIP-0026 §2)

Distributed-mode jobs MUST honor `min_trust_tier`. When set:

- The primary candidate MUST meet the tier.
- ALL `rpc_peers[]` MUST meet the tier.

A job that requested `min_trust_tier: trusted` and finds `< MIN_RPC_PEERS`
trusted RPC slices MUST 503 with the same shortfall body as §3, NOT
silently degrade.

### 8. UI: re-enabling "Distribute across all nodes"

When the Phase 4 of this IPIP lands (live network has ≥
`MIN_RPC_PEERS` daemons advertising `rpc.models`), `apps/web/app/chat/chat-view.js`
flips the checkbox back to enabled. Until then it stays disabled with
a tooltip pointing here.

## Rationale

**Why llama.cpp RPC and not vLLM, SGLang, or exo?** Audience.
Infernet operators already run llama.cpp under Ollama on consumer
GPUs; the GGUF format + tensor-split semantics are what they're
already used to. vLLM / SGLang assume cluster-of-trusted-machines and
their pipeline-parallel modes don't survive the adversarial threat
model. exo is closer in shape but hasn't stabilized its programmatic
API and bakes in iOS/Mac-friendly device discovery that conflicts
with Hyperswarm.

**Why fail closed instead of falling back to single-node?** Because
that's exactly what made IPIP-0031 a credibility hole. A user who
checks "Distribute across all nodes" deserves a real answer — either
the network actually distributes, or the network refuses. Silent
degradation produced months of misleading UX.

**Why `rpc:<model>` instead of reusing the IPIP-0032 `model:<id>`
topic?** Different capability. A node serving a model directly
(Ollama / llama.cpp single-process) is offering end-to-end inference;
a node hosting an RPC slice is offering a fragment that requires a
primary to compose. Mixing them in one topic would force every
discoverer to re-filter on `specs`. A separate kind keeps the swarm
membership cleanly scoped.

**Why a `_primary` capability flag and not "any node with the GGUF
can be primary"?** Hosting the primary requires holding embedding
weights + final-layer weights locally — substantially more memory
than hosting a middle-layer slice. Operators self-select. The flag
makes that explicit on the wire.

## Backwards compatibility

- **Petals daemon (`infernet inference serve --backend petals`):**
  marked deprecated in this release, removed in the next breaking
  release. Daemons running it keep working — they just aren't
  reachable through `distributed: true` on the control plane (the
  Petals proxy path is removed in §3 of this IPIP). A future
  housekeeping PR MAY drop `apps/cli/lib/inference/petals-*` entirely.
- **Existing chat UI:** the checkbox is disabled (§8) until Phase 4
  lands; existing Petals-served jobs already in flight finish via the
  legacy code path until it's pulled.
- **Heartbeat schema:** `specs.rpc` and `specs.rpc_primary` are new
  optional fields. Daemons that don't send them are simply not
  candidates for distributed mode — the `getProviders` and
  `pickChatProvider` paths are unchanged.
- **CPR receipts:** wire shape unchanged; only the pubkey resolution
  source changes.

## Reference implementation

Sketch only — no PR yet. Lands in three steps after this IPIP is Active:

1. **packages/rpc-adapter** — `spawnLlamaServer({ model, rpcPeers })`
   wrapper, stderr parser that extracts per-peer layer assignments,
   SSE framing helpers. Mirrors the existing `nim-adapter` shape.
2. **apps/cli additions:**
   - New `infernet inference serve --backend rpc --model <id>` —
     starts `rpc-server`, advertises in heartbeat, joins
     `rpc:<model>` topic via `@infernetprotocol/discovery`.
   - New `infernet inference primary --model <id>` — advertises
     `rpc_primary`, serves `/v1/rpc/inference`.
3. **apps/web changes:**
   - `apps/web/app/api/chat/stream/[jobId]/route.js` — new
     `runRpcProxy` branch replacing `runPetalsProxy` for
     `distributed: true` jobs. Old branch stays around guarded by
     `input_spec.fallback === "petals"` until removal.
   - `apps/web/app/chat/chat-view.js` — flip the checkbox back to
     enabled when `getRpcCandidates(model).length >= MIN_RPC_PEERS`.

Phasing:

1. **Phase 1 (this PR):** the IPIP, the docs flip, the disabled
   checkbox, the topic kind in IPIP-0032 (`rpc:`).
2. **Phase 2:** rpc-adapter package + daemon command + heartbeat
   schema.
3. **Phase 3:** control-plane proxy + per-peer layer attribution.
4. **Phase 4:** flip the chat checkbox back on, declare the IPIP
   `Active`.

## Test plan

**Unit.** `rpc-adapter`: parse llama.cpp stderr layer assignments
across 3 sample peers; verify CPR weight split sums to 1.0; verify
fail-closed when `< MIN_RPC_PEERS` candidates resolve.

**Integration.** Three Node processes on `localhost`: two `rpc-server`
slices on different ports + one primary serving `/v1/rpc/inference`.
The primary spawns `llama-server --rpc localhost:50052,localhost:50053`,
streams a known-prompt completion, and the test asserts:
- `routing` event lists both slices with disjoint layer ranges.
- Each slice received non-trivial computation (CPU/GPU time > 0).
- Killing one slice mid-stream produces a `peers[].status: "dropped"`
  in the next routing update.

**Network.** Two daemons on different VPSes hosting the same Qwen
2.5 70B GGUF, primary on a third. End-to-end chat through the
control plane returns a coherent completion in bounded time.

**Compatibility.** Old Petals daemon registered with
`specs.petals_models` — distributed-mode requests do not route to it
(§3 only filters on `specs.rpc.models`); single-node requests still
work through the existing `model:<id>` path.

## Security considerations

- **Untrusted RPC peers can return wrong tensors.** llama.cpp's RPC
  protocol is a trusted-cluster protocol — there's no built-in proof
  that an RPC peer ran the layer it claimed to run. Mitigations:
  - Run distributed mode at `min_trust_tier: verified` by default.
    `public` tier MAY be allowed but the chat UI MUST show a strong
    "unverified" warning.
  - Future IPIP: spot-check by re-running a random layer locally and
    comparing logits. Expensive; out of scope here.
- **DoS.** A peer can announce on the topic and then refuse to serve
  when dialed. Hyperswarm's per-peer disconnect is the first line;
  the primary SHOULD blacklist any peer that fails the RPC handshake
  twice in a 60s window.
- **Public exposure.** `rpc-server` listens on a TCP port — operators
  who want privacy MUST set `INFERNET_PUBLIC=0` (existing flag,
  IPIP-0006 §node-privacy); the daemon then joins `rpc:<model>` with
  `server: false` and the port is never advertised.

## Privacy considerations

- **Layer activations cross the network.** llama.cpp RPC ships
  intermediate activations between hosts. This is plaintext at the
  TCP layer. Anyone inspecting `rpc-server`'s socket sees activations
  for every prompt that flows through them. Mitigations:
  - Phase 1: document loudly that distributed mode currently exposes
    activations to RPC slice operators.
  - Phase 2: tunnel RPC over the encrypted Hyperswarm stream
    (Hyperswarm gives us a Noise-encrypted duplex; we can use it as
    the transport instead of plaintext TCP). Requires a small
    llama.cpp patch or a userspace proxy. Out of scope for this
    IPIP; named here so a follow-up IPIP can pick it up.
- **Pubkey ↔ model linkage.** A peer announcing `rpc:<model>` is
  publicly claiming "I host a slice of this model." Same trade-off
  as the model topic in IPIP-0032 — operators who want anonymity
  refuse to join `rpc:` topics.

## Open questions

- Should the primary be required to also serve a public `model:<id>`
  topic for the same model (so consumers always have a fallback)?
  Probably yes, but easy to add later.
- `MAX_RPC_PEERS = 8` is a guess. llama.cpp scales further but
  network round-trips eat the gain. Real measurement needed before
  finalization.
- Does `rpc_primary` need its own trust-tier filter, or does the
  job-level `min_trust_tier` already cover it (it's a regular
  provider, just with an extra capability)?
