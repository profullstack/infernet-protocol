## Abstract

Replaces the libp2p-Kademlia plan in IPIP-0006 Phase 4 and IPIP-0016
with **Hyperswarm**, a BitTorrent-style topic-keyed swarm DHT
(Holepunch / Pear runtime). Each Infernet daemon joins one swarm per
served model and one per workload class, computed as
`sha256("infernet:v1:<kind>:<value>")`. Peers serving the same model
or willing to accept the same workload class find each other directly,
with NAT traversal handled by Hyperswarm's UDP hole-punching against
its bootstrap nodes. The control plane stays the canonical source of
truth for reputation, payments, and identity links — but discovery
becomes a P2P swarm that survives the control plane going dark.

## Motivation

Today every job-routing decision flows through `/api/peers` and the
control plane's `providers` table. The system stops cold the moment
`infernetprotocol.com` is unreachable. IPIP-0006 Phase 1–3 already
named that as a problem and proposed libp2p Kademlia as the long-term
fix; IPIP-0016 specified it in detail. Two things changed since both
were written:

1. **Petals' DHT (the only DHT in the codebase) is moribund.** The
   upstream library hasn't shipped a release in roughly three years
   and Together AI — Petals' main backer — pivoted to commercial
   APIs. Building Infernet's discovery on top of Petals (or hivemind)
   ties us to a stack we don't control and can't easily upgrade.

2. **Hyperswarm reached production maturity.** Holepunch (formerly
   Hypercore Protocol) ships Pear runtime apps on top of it; the
   underlying DHT is the same one that powers Keet and a number of
   other live Hypercore-based applications. The library is JS-native,
   actively maintained, and the topic-keyed semantics map directly
   onto how Infernet thinks about discovery (one swarm per model, one
   swarm per workload class).

The shape we want is BitTorrent's: peers announce on a topic
(BitTorrent calls it an infohash; Hyperswarm calls it a topic key),
other peers find them by joining the same topic. No central registry.
Hyperswarm gives us that without introducing the IPFS / libp2p surface
area, and without forcing browsers into the path (the daemon is the
DHT participant; browsers continue to talk to the control plane and
to daemons over HTTPS).

## Specification

### 1. Library

Implementations MUST use `hyperswarm` (npm package, currently major
version 4.x) for DHT participation. Bootstrap is the package default
unless overridden. The CLI MAY pin a specific version in
`apps/cli/package.json`; the control plane does NOT join the DHT.

### 2. Topic key derivation

A **topic key** is exactly 32 bytes (SHA-256 output). Implementations
MUST derive topics as:

```
topic = sha256("infernet:v1:" + kind + ":" + value)
```

- The string is UTF-8.
- `kind` is the topic namespace; this IPIP defines the initial set.
- `value` is the namespace-specific identifier in canonical form.

Versioning lives in the `v1` segment of the prefix so a future IPIP
can rotate the topic space (e.g. to migrate to a different framing)
without colliding with v1 swarms still in flight.

### 3. Defined topic namespaces

| Kind     | Value (canonical form)                          | Meaning                                                           |
| -------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| `model`  | model id, lowercased, NFC normalized            | "I serve this model" — narrowest, used by chat router lookups.    |
| `class`  | one of `A`, `B`, `B5`, `C` (per IPIP-0010)      | "I'm available for this workload class" — broader.                |
| `node`   | x-only Nostr pubkey, lowercase hex (64 chars)   | "I am this specific node" — direct dial-by-pubkey.                |
| `rpc`    | model id, canonicalized as for `model`          | "I host a llama.cpp `rpc-server` for this model" (IPIP-0033).     |

Daemons MUST join `node:<their_pubkey>` and SHOULD join one
`model:<model_id>` per served model and one `class:<class>` per
workload class they accept. They SHOULD NOT join topics they cannot
serve — joining is a public claim of capability.

### 4. Peer handshake

When two peers connect via Hyperswarm, the daemon MUST perform a
signed handshake before any application data is exchanged:

```
INFERNET-HELLO\n
{
  "v": 1,
  "pubkey": "<x-only hex>",
  "topics": ["model:qwen2.5:7b", "class:B"],
  "address": "<advertised host[:port]>" | null,
  "ts": "<iso8601>",
  "nonce": "<base64url 16-byte>",
  "sig": "<bip340 schnorr over canonical(json minus sig)>"
}
\n
```

The signature MUST be a BIP-340 Schnorr signature over the canonical
JSON of every field except `sig`, using `@infernetprotocol/auth`'s
existing helper. The receiver MUST verify the signature, MUST drop
the connection on failure, and SHOULD record verified peers in a
short-lived in-memory cache keyed on pubkey.

Daemons running with `INFERNET_PUBLIC=0` (per IPIP-0006 §node-privacy)
MUST omit the `address` field. The handshake still proves identity;
the lack of an address signals "reachable only over relay / out of
band."

### 5. Bootstrap

Bootstrap is layered, in order of preference:

1. **Hyperswarm default bootstrap** — public Holepunch DHT entry
   nodes. The daemon trusts none of them with payload, only with
   first-contact peer routing.
2. **`/api/peers`** (IPIP-0006 Phase 1) — control-plane bootstrap
   list. Stays canonical for fresh installs and for nodes whose
   Hyperswarm bootstrap is firewalled. Returns the same JSON shape it
   does today, with one new optional field per row: `dht_topics` —
   a list of `kind:value` strings the peer is announcing on.
3. **`--bootstrap <multiaddr>`** — operator override. Implementations
   MUST accept this flag on `infernet start`.

The control plane MUST NOT itself join the DHT. The point of layering
is that `infernetprotocol.com` going dark stops degrading discovery
the moment a daemon has at least one DHT peer in its routing table.

### 6. Announce + lookup flow

A daemon serving the model `qwen2.5:7b`:

1. Computes `topic_model = sha256("infernet:v1:model:qwen2.5:7b")`.
2. Calls `swarm.join(topic_model, { server: true, client: true })`.
3. Hyperswarm announces the daemon's address against `topic_model`
   on the DHT and surfaces incoming connections via the swarm's
   `connection` event.
4. Repeats for `topic_class = sha256("infernet:v1:class:B")` and
   `topic_node = sha256("infernet:v1:node:<pubkey>")`.

A control plane / SDK / CLI looking for a `qwen2.5:7b` provider:

1. Computes the same `topic_model`.
2. Calls `swarm.join(topic_model, { client: true, server: false })`.
3. Treats incoming connections as candidates, runs the handshake (§4),
   filters by reputation / trust tier / liveness, and then routes the
   job over the same connection (job framing is OUT OF SCOPE for this
   IPIP — see follow-up).

### 7. Re-announce cadence

Daemons MUST re-announce on every served-set change (model added /
removed) AND at least every 10 minutes regardless. Hyperswarm
maintains its own DHT keepalive; this is the application-layer
liveness floor.

### 8. Browser clients

The browser playground does NOT join Hyperswarm. Browsers can't run
UDP. Discovery from the browser MUST go through `/api/peers` or
`/api/chat/provider` as today. The DHT is daemon-side only in this
IPIP.

### 9. Wire metadata for `/api/peers`

`/api/peers` MAY include `dht_topics` per row to help fresh nodes
prioritize which topics to join first (e.g. the most popular model
swarms). Required: implementations of `/api/peers` MUST NOT include
node IDs / pubkeys that have opted out via `is_public=false`.

## Rationale

**Why Hyperswarm and not js-libp2p Kademlia?** libp2p ships a much
larger surface area (multiplexers, transports, protocol negotiation,
PubSub, content routing) most of which we don't use. Hyperswarm is
~one library, one concept (topic keys), one event (connection). Less
to spec, less to break, less to maintain. The existing IPIP-0016
draft would have required us to re-spec a half dozen libp2p choices
that Hyperswarm makes for us out of the box.

**Why not roll our own DHT or piggyback on the public BitTorrent
mainline DHT?** Mainline (BEP-5 + BEP-44) was the strongest
alternative — millions of nodes, well-tested, `bittorrent-dht` is a
solid pure-JS implementation. Two reasons we didn't pick it:

1. It's optimized for "find peers for this 20-byte infohash," not
   "swarm with peers and exchange application data." We'd be
   reinventing Hyperswarm's connection layer on top.
2. Joining the public BitTorrent DHT puts Infernet daemons in the
   same DHT as actual BitTorrent peers, which both confuses observers
   ("are they pirating?") and exposes our peers to BitTorrent-flavored
   spam. Hyperswarm's bootstrap is logically separate.

Rolling our own is a non-starter. Discovery DHTs are notorious for
edge-case bugs (eclipse, partitioning, churn handling) and we have
no reason to write a new one.

**Why drop libp2p from IPIP-0006 entirely?** Phase 4 of IPIP-0006
called for libp2p Kademlia explicitly. With this IPIP, that phase is
moot — the DHT we add is Hyperswarm. IPIP-0006 should be revised
when this lands (or replaced outright). IPIP-0016, also Draft, is
fully replaced and should be marked as such.

**Why version the topic prefix?** A bare `sha256("model:qwen2.5:7b")`
locks us in. Including `infernet:v1:` lets a future IPIP redefine the
topic format (different encoding, different namespace, additional
metadata) without colliding with active v1 swarms. The cost is 12
bytes of input to the SHA-256 we were already computing.

## Backwards compatibility

- **Daemons on releases prior to this:** keep working. They never
  join the DHT, never announce; the control plane still has them via
  heartbeats. New daemons announce, but discoverers MUST still fall
  back to `/api/peers` so legacy daemons remain reachable.
- **Control plane:** no schema change required for the topic itself;
  `dht_topics` on `/api/peers` is an additive optional field.
- **Browsers:** unchanged — they never participated.
- **IPIP-0006:** Phase 4 (libp2p Kademlia) is superseded by this
  IPIP. A follow-up housekeeping PR SHOULD update IPIP-0006's text
  to point at IPIP-0032 instead of libp2p.
- **IPIP-0016:** moves from `Draft` to `Replaced`, with `replaces`
  pointing here.

## Reference implementation

Sketch only — no PR yet.

- New file: `packages/discovery/src/hyperswarm-node.js` — wraps
  `swarm.join()` for the four namespaces, runs the handshake on
  every incoming connection, exposes an event API the CLI consumes.
- `apps/cli/commands/start.js` — calls into the discovery package,
  joins per-served-model topics, handles re-announce on model add /
  remove.
- `apps/web/app/api/peers/route.js` — adds `dht_topics` to each row
  when the underlying provider has registered any.
- `apps/cli/lib/runtime-config.js` — accepts a `discovery: { enabled,
  bootstrap[] }` block.
- `tests/discovery-handshake.test.js` — round-trip the handshake
  envelope, verify good signature accepted, tampered signature
  rejected, address field omitted when `INFERNET_PUBLIC=0`.

Phasing:

1. Discovery package + handshake helpers (no daemon wiring yet).
2. CLI joins on `infernet start`, per-served-model topics; gated
   behind `--enable-dht` for one release.
3. Discoverers (CLI + control-plane SDK helpers) prefer the DHT,
   fall back to `/api/peers`.
4. Default `--enable-dht` on; flag becomes `--no-dht`.

## Test plan

**Unit.** Round-trip `signHandshake` / `verifyHandshake` (good,
tampered, replayed nonce, missing field). Topic key derivation —
golden vectors for `model:qwen2.5:7b`, `class:B5`, and a node pubkey.

**Integration.** Two Node processes on `localhost`, each spinning
up a `hyperswarm` instance, joining the same topic, exchanging the
handshake, and confirming both see each other in their `connection`
handler. A third process joins `client: true, server: false`, queries
the topic, asserts both servers appear within a bounded time.

**Compatibility.** Legacy daemon (no DHT) registered via
`/api/peers` — discoverer with DHT enabled still finds it via the
fallback path, and the legacy daemon still receives jobs.

**Resilience.** Kill one bootstrap node mid-session; verify the swarm
re-bootstraps from the others within `KEEPALIVE_MS * 2`.

## Security considerations

- **Sybil.** A DHT can't authenticate "is this peer real?" — the
  handshake authenticates "this peer holds the private key for this
  pubkey." Sybil resistance therefore lives in the same place it
  lives today: reputation (IPIP-0007 / CPR receipts) and trust tiers
  (IPIP-0026 §2). DHT lookups MUST filter by trust tier and
  reputation before routing.
- **Eclipse.** A peer can be eclipsed if every bootstrap node is
  compromised. Mitigated by layering: Hyperswarm's bootstrap +
  `/api/peers` + operator-supplied `--bootstrap`. Compromise requires
  all three.
- **DoS via topic flooding.** A malicious peer could announce on
  thousands of topics. Hyperswarm rate-limits at the protocol layer;
  Infernet's own rate-limit lives at the handshake layer (drop a
  peer that opens too many connections without serving any).
- **Address leakage.** A peer that joins a topic *will* be reachable
  by any other peer on that topic — that's the point. Operators who
  want privacy MUST set `INFERNET_PUBLIC=0`; the daemon then runs
  `client: true, server: false` and never announces a routable
  address.

## Privacy considerations

- **DHT exposes reachable address.** Same caveat as IPIP-0006: a
  peer that announces with a public address can be enumerated. The
  existing `is_public` opt-out in the providers / aggregators /
  clients tables MUST gate DHT announcement: when `is_public=false`,
  the daemon MUST NOT call `swarm.join` with `server: true`.
- **Topic enumeration.** Anyone can compute `sha256("infernet:v1:
  model:<x>")` for any model name; the topic space is therefore as
  enumerable as the model namespace. This is intentional — clients
  need to compute the same topic without coordination — but it
  means the DHT can't carry confidential model lists. Operators
  serving private models MUST NOT announce them via topic; rely on
  `node:<pubkey>` plus out-of-band coordination instead.
- **Pubkey linkage.** Joining `node:<pubkey>` ties a Nostr identity
  to a network address. Same trade-off as today; the operator can
  refuse to join `node:` topics if they want pubkey-anonymous
  participation, at the cost of direct dial-by-pubkey.

## Open questions

- Do we want a fifth namespace (`region:` or `gpu:vendor:nvidia`) for
  hardware-aware routing? Easy to add later; no need to spec now.
- Should `/api/peers` start filtering by `dht_topics` (`?topic=...`)
  to let lightweight clients pre-enrich without joining the DHT?
  Probably yes; out of scope for this IPIP.
- Hyperswarm's default bootstrap is Holepunch-operated. Should
  Infernet run our own bootstrap nodes as a hedge? Cheap — one VPS,
  ~$5/mo per geo. Worth doing once daemon adoption justifies it.
