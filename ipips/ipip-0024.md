## Abstract

Changes how providers emit token events to the control plane so that
each `job_events` row carries a multi-token text chunk instead of a
single model token. This reduces the number of Supabase Realtime
pushes from one-per-model-token to one-per-flush-interval, cutting
the perceived streaming latency from ~150 ms per character to ~150 ms
per chunk (~16–32 characters), a ~10–20× improvement with no changes
to the client-facing SSE protocol.

## Motivation

The current P2P token streaming path is:

```
Ollama → MSG.TOKEN (1 char) → EventBuffer (batch 16 events)
       → POST /api/v1/node/jobs/:id/events (16 rows)
       → supabase.insert(rows)           (one INSERT, 16 rows)
       → Supabase Realtime fires 16 times (one per row)
       → 16 SSE frames to the browser    (each ~150 ms apart)
```

Ollama's NDJSON stream emits one JSON object per BPE token. For
models with aggressive tokenisation (GLM4, Qwen, Mistral), most
tokens are 1–3 characters. The daemon already batches up to 16
of these into a single HTTP request (IPIP-0009, `EVENT_BATCH_MAX
= 16`), but the server inserts them as 16 separate rows. Supabase
Realtime fires once per row regardless of INSERT batch size. The
result is that a 512-token response (~1000 characters) triggers
~512 Realtime pushes, each adding ~150 ms of round-trip latency
on top of the actual generation time. The practical effect:
streaming feels like one character appears every ~150 ms even
when the GPU is generating at 50+ tokens/second.

The fix is trivial: merge all `token` events within a flush
window into a single row before inserting. One flush = one row =
one Realtime push = one SSE frame. Latency drops from
`n_tokens × 150 ms` to `n_flushes × 150 ms`.

## Specification

### 1. Provider-side change (`apps/cli/lib/chat-executor.js`)

`EventBuffer.flush()` MUST merge all queued `token` events into
a single `token` event before writing to the control plane.
Non-token events (meta, done, error) MUST be left as individual
events and preserve their order relative to the merged token.

Merging algorithm:

```
input:  [meta, token("H"), token("el"), token("lo"), done]
output: [meta, token("Hello"), done]
```

If there are no token events in the batch, the flush proceeds
unchanged.

The merge MUST concatenate `event.data.text` values in the order
they were received. No other fields of the token event data are
affected.

Reference implementation:

```js
flush() {
    if (this.events.length === 0) return;
    const merged = mergeTokens(this.events);
    this.events = [];
    this.lastFlush = Date.now();
    return this.client.postJobEvents(this.jobId, merged);
}

function mergeTokens(events) {
    const out = [];
    let tokenText = "";
    for (const ev of events) {
        if (ev.event_type === "token") {
            tokenText += ev.data?.text ?? "";
        } else {
            if (tokenText) {
                out.push({ event_type: "token", data: { text: tokenText } });
                tokenText = "";
            }
            out.push(ev);
        }
    }
    if (tokenText) {
        out.push({ event_type: "token", data: { text: tokenText } });
    }
    return out;
}
```

### 2. Protocol clarification

Prior to this IPIP the `token` event was implicitly described as
carrying a single model token. This IPIP clarifies:

> A `token` event's `data.text` field MAY contain more than one
> model token's text. Consumers MUST NOT assume each `token` event
> corresponds to exactly one BPE/SPM token. The only guarantee is
> that concatenating all `token.data.text` values in order
> reconstructs the full assistant message.

This is backwards-compatible: existing consumers already
concatenate `data.text` into an accumulator string; the change
is invisible to them.

### 3. Server-side — no change required

`emitJobEvents` in `node-api.js` already bulk-inserts an array of
rows in a single Supabase call. After this change, most flushes
contain exactly one `token` row instead of 16, so the INSERT is
smaller but the logic is identical.

### 4. Flush parameters

The existing flush parameters (`EVENT_BATCH_MAX = 16`,
`EVENT_BATCH_FLUSH_MS = 250`) are unchanged. They now govern
how many model tokens are merged into one chunk before the
single POST is made, rather than how many rows are sent per POST.

Implementers MAY raise `EVENT_BATCH_MAX` (e.g. to 64) now that
the per-row Realtime cost is gone, accepting larger chunks for
even lower overhead. The default stays at 16 to keep latency
under 250 ms even at low generation speeds.

### 5. Affected files

- `apps/cli/lib/chat-executor.js` — `EventBuffer.flush()` + new
  `mergeTokens()` helper.
- No changes to `apps/web/`, `packages/engine/`, or
  `supabase/migrations/`.

## Rationale

**Why merge at the daemon instead of the server?** The server
(`emitJobEvents`) already does a single INSERT for the whole
batch. The Realtime fan-out is per-row, not per-INSERT. Merging
at the daemon before the POST reduces row count before the INSERT,
which is the only lever that reduces Realtime events.

**Why not change the Realtime subscription to batch client-side?**
Supabase Realtime sends one Postgres change notification per row.
There is no client-side batching API. The only way to reduce
Realtime overhead is to reduce row count.

**Why not use a dedicated streaming channel instead of Realtime?**
That would require a persistent connection from the provider to
the control plane, NAT traversal, and a new protocol surface.
Supabase Realtime is already the right tool for event fan-out;
the problem was row count, not the transport.

**Why not switch to WebSockets?** SSE is correct for unidirectional
server-to-client streaming. WebSockets add bidirectional complexity
that is not needed here. The bottleneck was Realtime row count, not
the final-mile SSE transport.

**Why keep `EVENT_BATCH_MAX` at 16?** At 250 ms flush interval, a
provider generating 50 tok/s accumulates ~12 tokens per flush. 16
is a safe ceiling that keeps the merged chunk from becoming too
large (~128 characters). Operators on faster hardware can raise
it via `config.engine.eventBatchMax` without a protocol change.

## Backwards compatibility

The `token` event shape is unchanged: `{ event_type: "token",
data: { text: string } }`. The only difference is that `text`
may now contain more than one model token's worth of characters.

All existing consumers (chat-view.js, chat-stream.js, the OpenAI
compat route) already concatenate `data.text` into a running
accumulator. No consumer-side changes are required.

Providers running older daemon versions continue to send one token
per event. They will be slower than updated providers but the
protocol is not broken. Providers SHOULD upgrade to this version
as it is a pure performance win with no trade-offs.

## Reference implementation

`apps/cli/lib/chat-executor.js` — `mergeTokens` helper + updated
`EventBuffer.flush()`. Diff is under 20 lines.

## Test plan

### Unit (`tests/chat-executor.test.js` or equivalent)

- `mergeTokens([])` returns `[]`.
- `mergeTokens([token("a"), token("b"), token("c")])` returns
  `[token("abc")]`.
- `mergeTokens([meta, token("a"), token("b"), done])` returns
  `[meta, token("ab"), done]`.
- `mergeTokens([meta, done])` returns `[meta, done]` (no tokens).
- `mergeTokens([token("a"), error])` returns `[token("a"), error]`.

### Integration

- Start a daemon with a mock engine that emits 50 single-char
  tokens. Verify `job_events` contains exactly 3–5 rows (meta + 3–4
  merged-token batches + done) instead of 52.
- End-to-end: submit a chat job on /chat. Measure time from first
  token to last token. Verify it's proportional to generation time,
  not `n_tokens × 150 ms`.

## Security considerations

Merging token text at the daemon does not change the trust model.
The provider is already trusted to emit accurate token data; merging
concatenates that data before it is signed and posted. No new
attack surface.

## Privacy considerations

No change. Token text content is unchanged; it is still transmitted
over the signed provider channel and stored in `job_events` exactly
as before.

## Open questions

- Should `EVENT_BATCH_MAX` be raised from 16 to 64 in this same
  change, or left at 16 and raised later once the improvement is
  measured in production?
- Should the server enforce a `max_text_length` per token event
  (e.g. 4096 chars) to guard against a runaway merger? Currently
  `EVENT_BATCH_MAX = 16` provides an implicit ceiling.
