## Abstract

Extends the NIP-44 E2E encryption model (IPIP-0027) from a simple
consumer↔node bilateral channel to a three-party key hierarchy:

```
Consumer ←─ NIP-44 ─→ Node ←─ NIP-44 ─→ Model
```

Each trained model (IPIP-0023) is assigned its own secp256k1 keypair
at training time. The model's private key is stored only inside the
node operator's encrypted model artifact and inside TEE memory during
inference (IPIP-0026 Phase 3). The model's public key is advertised
alongside the node's public key. This enables:

1. **Consumer → Model channel**: the consumer can encrypt a prompt
   to the *model's* pubkey, not just the node's. A node that
   hosts multiple models can't mix up which model decrypts which job.
2. **Model attribution**: a model can sign its response with its
   private key. The consumer verifies the signature, proving the
   response came from that specific model weights, not from the node
   operator substituting a different model.
3. **Scaled P2P routing**: when a single inference job spans
   multiple nodes (model sharding, IPIP-0023 workload classes C/D),
   each shard gets its own key. The aggregator node holds the
   consumer ↔ model outer key; inner shard keys are negotiated
   node ↔ node without exposing the consumer's key material.

## Motivation

IPIP-0027 solves the consumer ↔ single-node case: the node derives
the shared secret and decrypts the prompt for inference. But the
IPIP-0027 model has two scalability gaps:

1. **Multiple models per node**: a node serving 10 models all
   decrypt with the same node privkey. A compromised node key leaks
   all model conversations simultaneously. Model-specific keys
   limit blast radius per model.

2. **Multi-node inference**: workload classes C1–D4 (IPIP-0023)
   distribute a job across N nodes. Today there is no protocol for
   the aggregator to pass encrypted activations between shards
   without every shard learning the consumer's privkey.

The model keypair is the natural unit of trust for inference:
weights, key, and attestation certificate travel together.

## Specification

### 1. Model keypair

When a model artifact is trained or imported (IPIP-0023 §4.3):

1. The CLI generates a fresh secp256k1 keypair for the model:
   ```
   model_privkey = random_bytes(32)
   model_pubkey  = secp256k1_pubkey(model_privkey)
   ```
2. `model_privkey` is AES-256-GCM encrypted with the node operator's
   Nostr pubkey (same ECDH mechanism as IPIP-0027) and stored inside
   the model artifact bundle alongside the weights.
3. `model_pubkey` is advertised in the provider heartbeat:
   ```json
   {
     "specs": {
       "served_models": ["qwen2.5:7b"],
       "model_keys": {
         "qwen2.5:7b": "hex64pubkey"
       }
     }
   }
   ```
4. The control plane MUST expose `model_keys` in the
   `GET /api/chat/provider` response (IPIP-0027 §9) so consumers
   can encrypt to the model key rather than (or in addition to)
   the node key.

### 2. Consumer → Model encryption

The consumer performs NIP-44 key derivation with the model pubkey
instead of the node pubkey:

```
consumer_ephemeral_keypair = generateKeyPair()
conv_key = NIP44_getConversationKey(consumer_priv, model_pub)
encrypted_messages = NIP44_encrypt(conv_key, JSON.stringify(messages))
```

The POST to `/api/chat` carries:
```json
{
  "encryptedMessages": "...",
  "clientPubkey": "hex64",
  "modelPubkey": "hex64",
  "providerId": "uuid"
}
```

The `modelPubkey` field distinguishes model-keyed jobs from
node-keyed jobs (IPIP-0027).

### 3. Node decryption path (single-node)

The daemon:
1. Reads `input_spec.encrypted_messages` and `jobs.client_pubkey`.
2. Looks up `model_privkey` from the model artifact bundle (decrypted
   with the node operator's Nostr privkey).
3. Derives: `conv_key = NIP44_getConversationKey(model_priv, client_pubkey)`.
4. Decrypts messages → runs inference.
5. Re-encrypts each token chunk with the same `conv_key`.

### 4. Multi-node inference (aggregator pattern)

For sharded workloads (workload classes C2, D2+):

```
Consumer
   │
   │  NIP-44(consumer_priv, model_pub)
   ▼
Aggregator Node (holds model_privkey)
   │
   │  NIP-44(aggregator_priv, shard_pub) for each shard
   ▼
Shard Node 1 ... Shard Node N
```

- The aggregator decrypts the consumer payload using the model key.
- The aggregator re-encrypts each shard's portion of the activations
  using a fresh ephemeral key per shard, derived from the aggregator's
  node privkey and the shard node's pubkey.
- Shard nodes never learn the consumer's key material.
- The aggregator collects shard outputs, re-encrypts the assembled
  response using the consumer conv_key, and writes it to `job_events`.

This is the standard "onion routing of activations" pattern used by
confidential MPC inference research, simplified for the single-
aggregator case.

### 5. Model response signing (optional, Phase 2)

When `input_spec.require_model_sig = true`:

- The model signs the full response text with `model_privkey` using
  Schnorr (BIP-340, same as Nostr).
- The daemon includes the signature in the `done` event:
  ```json
  { "encrypted_text": "...", "model_sig": "hex128" }
  ```
- The consumer verifies:
  `schnorr.verify(model_sig, sha256(response_text), model_pubkey)`
- If verification fails, the consumer UI shows a warning:
  ```
  ⚠ Response signature invalid — model identity unverified.
  ```

### 6. Key rotation

Model keys SHOULD be rotated:
- On every new model release (new weights = new key).
- When the node operator's Nostr key is rotated.
- Never mid-conversation (conversation key is derived at job
  creation; rotation takes effect on the next job).

The control plane MUST NOT cache model pubkeys beyond the heartbeat
interval (60s). Clients MUST re-fetch `GET /api/chat/provider`
before each new conversation, not each token.

### 7. `GET /api/chat/provider` response extension

```json
{
  "providerId": "uuid",
  "providerPubkey": "hex64",
  "modelPubkey": "hex64",
  "model": "qwen2.5:7b",
  "reservedUntil": "<iso8601>"
}
```

`modelPubkey` is null when the provider has not yet generated model
keys (legacy provider). In that case the client falls back to
node-keyed encryption (IPIP-0027).

## Rationale

**Why not just use the node key for everything?** Node keys are
tied to the node identity and rotate infrequently. Model keys are
tied to model weights and rotate with each model release. Separate
keys enable separate audit trails, separate reputation signals,
and separate blast radii on compromise.

**Why Schnorr for model signing?** The node already uses Schnorr
(BIP-340) for request authentication (IPIP-0003). Re-using the
same signature scheme means the verification library is already
present on both sides.

**Why not include the model privkey in the TEE attestation
measurement?** The TEE measurement commits to the software image,
not to ephemeral key material. The model privkey is ephemeral from
the TEE's perspective (loaded from the encrypted artifact at
startup). The attestation proves the software handling the key is
unmodified; the key itself proves the model identity. Both are
needed for full assurance.

**Multi-node / shard path — why aggregator re-encryption rather
than direct consumer ↔ shard keys?** Because the consumer doesn't
know which shards will be assigned at job creation time. The
aggregator knows. Re-encrypting at the aggregator boundary is the
lowest-latency option that preserves consumer key isolation.

## Backwards compatibility

- `modelPubkey` is a new optional field in the provider response.
  Legacy providers return null; clients fall back to IPIP-0027
  node-keyed encryption.
- `jobs.model_pubkey` is a new nullable column:
  ```sql
  alter table jobs add column if not exists model_pubkey text;
  ```
- Existing node-keyed jobs are unaffected.

## Reference implementation

Phase 1 (single-node model keys):
- `apps/cli/lib/model-key.js` — generate/load model keypair from artifact
- `apps/cli/lib/chat-executor.js` — decrypt with model_privkey when present
- `apps/web/app/api/chat/provider/route.js` — expose modelPubkey
- `apps/web/app/chat/chat-view.js` — encrypt to modelPubkey when available

Phase 2 (model response signing):
- `apps/cli/lib/chat-executor.js` — sign done event with model_privkey
- `apps/web/app/chat/chat-view.js` — verify model_sig on done event

Phase 3 (multi-node / aggregator):
- `apps/cli/lib/aggregator.js` — new module
- IPIP-0023 milestone 6 (distributed aggregation)

## Test plan

### Unit

- Model keypair: `encrypt(node_priv, model_priv)` → `decrypt(node_priv, ...)` round-trip.
- Consumer → model: `NIP44_encrypt(consumer_priv, model_pub, msg)` → node decrypts with
  `model_priv + client_pub` → same message.
- ECDH symmetry across 3 parties (consumer, node, model) — no cross-key decryption possible.
- Schnorr sign/verify: valid model sig passes, tampered response fails.

### Integration

- Node with model key: registers with `model_keys` in heartbeat.
  `GET /api/chat/provider` returns `modelPubkey`.
  Browser encrypts to modelPubkey. Daemon decrypts with model_privkey.
  Consumer receives and decrypts tokens.
- Legacy node (no model key): browser falls back to node-keyed
  encryption (IPIP-0027). No error.

## Security considerations

- The model privkey is only as secure as the node operator's Nostr
  privkey (used to decrypt it from the artifact). TEE attestation
  (IPIP-0026 Phase 3) provides the strongest guarantee that the key
  is handled correctly.
- For non-TEE nodes, model key encryption is a deterrence measure,
  not a hard guarantee. A determined node operator could extract the
  model privkey from the artifact if they also hold their own Nostr
  privkey.
- The aggregator re-encryption pattern (§4) means the aggregator
  node sees plaintext activations between shards. This is the same
  trust assumption as IPIP-0027 (the assigned provider sees plaintext
  during inference). TEE attestation on the aggregator addresses this.

## Open questions

- Should model privkeys be generated inside a TEE so even the node
  operator can't extract them? (Requires IPIP-0026 Phase 3 to land
  first on the model-serving nodes.)
- Should model pubkeys be registered on a Nostr relay so consumers
  can verify them independently of the control plane?
- For the multi-node path, should shard-to-shard encryption use
  ephemeral DH keys per activation batch, or a persistent session key
  for the duration of the job?
